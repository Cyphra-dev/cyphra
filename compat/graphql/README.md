# compat-graphql

Private workspace (not published). It proves that a GraphQL-over-Neo4j implementation exposes the
same API as `@neo4j/graphql` v7 (pinned to an exact version in `package.json`): same printed SDL and
same results for the same operations on the same data. The goal is that teams can switch to
`@cyphra/graphql` without changing their frontend queries (#68).

## Layout

```
fixtures/<app>/
  typeDefs.graphql            v7 type definitions (@node, @relationship, @cypher, @authorization, ...)
  seed.cypher                 data; statements end with `;` at end of line, `//` comment lines
  operations/NN-name.graphql  one operation per file (header comments, see below)
  operations/NN-name.variables.json   optional variables
  operations/NN-name.jwt.json         optional decoded JWT payload (passed as context `jwt`)
golden/<app>/schema.graphql   lexicographicSortSchema + printSchema of the reference schema
golden/<app>/NN-name.json     normalized result of each operation
src/implementations.ts        the GraphQLImplementation adapters (@neo4j/graphql, @cyphra/graphql)
cyphra-expected.json          checks @cyphra/graphql must pass (progress mode, see below)
REPORT.md                     generated compatibility report
```

Every operation runs on a freshly reset database (everything deleted, fixture seed applied), so
operations are independent and mutations can be compared.

## Running

All commands need a disposable Neo4j 5 with APOC (it is wiped between operations):

```sh
docker run -d --name cyphra-compat -p 127.0.0.1:17688:7687 \
  -e NEO4J_AUTH=neo4j/cyphra_ci_test -e NEO4J_PLUGINS='["apoc"]' neo4j:5-community
export NEO4J_TEST_URI=bolt://127.0.0.1:17688 NEO4J_TEST_USER=neo4j NEO4J_TEST_PASSWORD=cyphra_ci_test

pnpm --filter compat-graphql test     # goldens still match (CI: neo4j-integration job)
pnpm --filter compat-graphql golden   # regenerate goldens from @neo4j/graphql, then REPORT.md
pnpm --filter compat-graphql report   # compare every implementation, write REPORT.md
pnpm --filter compat-graphql golden movies   # only some fixtures (REPORT.md not written)
pnpm --filter compat-graphql report --update-expected   # also rewrite cyphra-expected.json
```

`test` is skipped when the `NEO4J_TEST_*` variables are unset. Scripts run with `TZ=UTC`:
`@neo4j/graphql` parses `Date` inputs in the process time zone.

## Adding a fixture or an operation

1. Create `fixtures/<app>/typeDefs.graphql` and `seed.cypher` (use fixed ids in the seed so results
   are stable; ids generated by `@id` are masked).
2. Add `operations/NN-name.graphql`. Header comment lines at the top of the file:
   - `# features: filter.string, sort` tags used to group the report by feature;
   - `# ordered` when array order is part of the expected result (sort, pagination). Without it,
     every array in the result is sorted before comparison, because Neo4j order is unspecified.
3. Optional `NN-name.variables.json` and `NN-name.jwt.json`.
4. Run `pnpm --filter compat-graphql golden`, read the new golden files to check the results are
   what `@neo4j/graphql` really returns, and commit them with `REPORT.md`.

Normalization: UUIDs become `<generated-id>`, datetimes within a day of the run become
`<generated-datetime>` (seed datetimes must be old), floats are rounded to 12 significant digits,
and errors keep only `message`, `path` and `extensions.code`.

Bumping `@neo4j/graphql`: change the exact version, run `golden`, and review the golden diff: it is
the list of API changes the other implementations must follow.

## Plugging in another implementation

`src/implementations.ts` defines:

```ts
type GraphQLImplementation = {
  name: string;
  skipReason?: () => Promise<string | undefined>;
  buildSchema(
    typeDefs: string,
    options: { driver: Driver; jwt: { key: string } },
  ): Promise<GraphQLSchema>;
  contextFor(op: Operation): Record<string, unknown>;
};
```

`@cyphra/graphql` is registered with `compat.v7.makeSchema({ typeDefs, driver })` and checked
against the same goldens. `skipReason` lets an adapter opt out (the check is then `skipped`).

## Progress mode

The reference must pass every check. Other implementations are measured against
`cyphra-expected.json`, the list of checks (`<fixture>/schema` or `<fixture>/<operation>`) they must
pass:

- a listed check that fails is a regression: `test` fails;
- a check that passes but is not listed also fails `test`, with a hint to add it, so the list always
  matches reality.

After making more operations pass, run `report --update-expected` and commit the list with
`REPORT.md`. `report` prints regressions and new passes and exits with 1 when there are any.

## Reading the report

`REPORT.md` has a summary per implementation (pass / fail / skipped), a table per feature tag
(`pass`, `partial` when some checks are skipped, `FAIL`), and a table per fixture listing the
`schema` check and every operation. A failing check shows why (SDL or output differs from golden,
or the implementation threw); run `test` for the full diff.
