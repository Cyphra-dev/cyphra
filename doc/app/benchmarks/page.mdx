# Benchmarks

**What does the ORM layer cost?** These benchmarks run the same operations on the same Neo4j data
through the raw [`neo4j-driver`](/compare/neo4j-driver) with hand-written Cypher (the baseline),
the Cyphra typed client, [neogma](/compare/neogma-neode), and, for GraphQL,
[`@neo4j/graphql`](/compare/neo4j-graphql-library) against [`@cyphra/graphql`](/graphql). The
scripts are in [`bench/`](https://github.com/Cyphra-dev/cyphra/tree/main/bench) and run with one
command against a Neo4j in Docker.

What the published run shows (numbers below, from the run dated in [Environment](#environment)):

- **Most operations are one statement.** A `create` (nested creates and connects included),
  `update`, `upsert`, a `delete` with `onDelete` cascades, and the reads compile to a single
  Cypher statement that also returns the result, so on Bolt Cyphra is within about 20% of
  hand-written Cypher on every scenario: update +2%, nested create of a user with 5 posts
  +11% (it used to send 12 statements and cost 4× the baseline), create +16%, cascading delete
  +17%. Reads stay within about 10%; differences of that size are noise on this machine.
- **Shortest path is +13%** (re-run on its own after the rest of the suite, same machine and
  method). Cyphra's statement does about the same work in Neo4j as the hand-written one; on the
  client, decoding the typed path no longer re-reads the schema for every node or builds nodes it
  throws away, and `DateTime` values are converted without `neo4j-driver`'s text round trip. The
  +47% of the first run was mostly noise on this machine.
- **Over HTTP, an operation is one request.** A single statement that writes nothing when it fails
  goes out as one auto-commit Query API request, like the `fetch` baseline, so Cyphra over HTTP is
  within about 20% of it (it was 1.2× to 9× before).
- **`@cyphra/graphql` is faster than `@neo4j/graphql`** on 8 of the 9 shared operations (by 18%
  to 32% on the median, 2% on findMany), and level on the aggregation.
- **neogma is often faster than the raw baseline** on simple operations, because it uses
  auto-commit transactions (see [Caveats](#caveats)), but it has no API for half of the scenarios.

Single-digit percentages are within the noise of this run: compare the p95 column before reading
much into them.

for edge runtimes) against the same hand-written Cypher sent to the Query API with `fetch`, and
against the Bolt baseline.

<HttpTable results={results} />

An operation that compiles to one statement and writes nothing when it fails (every scenario here)
is one auto-commit request, the same as the `fetch` baseline: the difference is the work on the
client. Operations that need an explicit transaction (a nested `connect`, checked after the
statement ran, or anything inside `$transaction`) add one request to commit.

## GraphQL

`@cyphra/graphql` and `@neo4j/graphql` 7.6.8 serve the same type definitions on the same driver.
Each operation is parsed and validated once, then run with `execute()`, as a server with a
document cache would.

<GraphqlTable results={results} />

Both libraries compile each GraphQL operation to one Cypher statement, so the difference is the
time spent building that statement and shaping the result. `@cyphra/graphql` is level on the
aggregation (it reads the same nodes) and ahead elsewhere.

## Method

- **Data.** 10,000 users following 5 others each (50,000 edges), 10,000 posts by the first 2,000
  users, 2 comments per post, and 1,000 documents with 384-dimension embeddings, seeded with a
  fixed random seed. Constraints and indexes are the ones `cyphra push` creates from the
  benchmark schema: unique ids and emails, a range index on `User.age`, a cosine vector index.
- **Same conditions.** Every Bolt contender uses `neo4j-driver` 6.3.2 with default settings and
  the explicit database `neo4j`. Cyphra, the GraphQL libraries and the baseline share one driver;
  neogma always creates its own, from the same version. Every contender walks the same inputs in
  the same order.
- **Same answers.** Before timing, the first result of each contender is compared with the
  baseline's (rows, counts, ids), and writes are checked in the database (5 posts after the nested
  create, nothing left after the cascading delete).
- **Timing.** [tinybench](https://github.com/tinylibs/tinybench) 6, chosen over mitata because
  these are asynchronous I/O-bound calls (where mitata's CPU-level counters do not apply) and the
  delete scenario needs an unmeasured `beforeEach`. Each scenario runs 3 interleaved rounds; in
  each, every contender warms up, then runs at least 70 iterations and 1 second. The order rotates
  between rounds and the samples are merged, so noise on the machine spreads over all contenders.
- **The baseline** opens a session per call and runs one statement in a managed transaction
  (`executeRead` / `executeWrite`, which retry transient errors), as Cyphra does, and maps records
  to plain objects (integers to numbers, temporals to `Date`).

## Caveats

- **Loopback, one machine.** Neo4j runs in Docker next to the benchmark, so there is no network
  latency: the best case for showing client-side overhead. Over a network, each call gains the
  round-trip time and the relative overhead gets smaller.
- **A shared machine.** Other processes ran during the published run. Interleaving spreads that
  noise; it does not remove it. Differences of a few percent are within the noise, and the p95
  shows the spread.
- **No disk flush.** The database runs on a tmpfs, so commits do not wait for the transaction log
  to reach a disk (on a shared machine that wait is large and erratic). On real storage each write
  gains that time, the same for every library, and the relative write overhead gets smaller.
- **Transaction patterns differ.** neogma runs reads and single writes as auto-commit statements
  (`session.run`), one round trip less than a managed transaction, without retries; that, rather
  than less work, is why it can beat the baseline on simple reads.
- **Sequential calls only.** Throughput under concurrency is not measured.
- **A small, cached data set.** The graph fits in memory, so the numbers show the client side
  (building the query, parameters, mapping results) and the statement each library sends, not
  Neo4j's disk.
