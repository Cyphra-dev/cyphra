# Migrations

Neo4j is schemaless, so a Cyphra migration does two jobs: keep **constraints and indexes** in line
with your schema, and fix up **existing data** when the schema changes (backfill new defaults, refuse
to continue when a newly required field is missing, and so on).

## Workflow

```bash
cyphra dev                         # local Neo4j in Docker, writes .env
# edit schema.cyphra
cyphra migrate dev --name add-roles   # generate a migration from your changes, then apply it
cyphra migrate status              # what is applied, pending, modified, or not yet captured
cyphra migrate deploy              # CI / production: apply pending migrations only
```

`cyphra migrate dev` compares your schema with **`migrations/schema.snapshot.json`** (the schema as of
the last generated migration) and writes `migrations/<timestamp>_<name>.mjs`. Generation needs no
database and is deterministic, so the file can be reviewed like any other code. Commit both the
migration and the snapshot.

- `cyphra migrate diff` prints what would be generated, without writing anything.
- `cyphra migrate dev --create-only` writes the migration without applying it, so you can edit it first.

## What gets generated

| Schema change                                    | Generated step                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------- |
| new `@id` / `@unique` / `@index`                 | `CREATE CONSTRAINT / RANGE INDEX … IF NOT EXISTS`                   |
| removed or changed `@id` / `@unique` / `@index`  | `DROP CONSTRAINT / INDEX … IF EXISTS`                               |
| new field with a `@default` on an existing model | backfill: `MATCH (n:User) WHERE n.role IS NULL SET n.role = $value` |
| field becomes required and has a default         | backfill of the missing values                                      |
| new required field without a default             | **guard**: the migration fails if any existing node lacks it        |
| removed field / model                            | `REMOVE` / `DETACH DELETE`, **commented out**: you opt in           |
| type change, or a likely rename                  | a review warning at the top of the file                             |

Steps run in this order: drop obsolete DDL → data steps → create new DDL, so values are backfilled
before a uniqueness constraint is created on them. `now()` backfills with `datetime()` / `date()` and
`uuid()` with `randomUUID()`. `cuid()` cannot be generated in Cypher, so it also falls back to `randomUUID()`.

Example, after adding `role String @default("member")` and `handle String @unique` to `User`:

```js
// Generated by `cyphra migrate dev`. Review it before applying to shared databases.
import { defineMigration } from "cyphra";

export default defineMigration({
  name: "20261118174710_add-roles",
  async up({ db }) {
    // Backfill User.role with its default on existing nodes.
    await db.execute("MATCH (n:`User`) WHERE n.`role` IS NULL SET n.`role` = $value", {
      value: "member",
    });

    // User.handle is now required and has no default: make sure no existing node lacks it.
    {
      const [row] = await db.execute(
        "MATCH (n:`User`) WHERE n.`handle` IS NULL RETURN count(n) AS count",
      );
      if (row && Number(row.count) > 0) {
        throw new Error("User.handle is required but some existing User nodes do not have it. …");
      }
    }

    // Create constraint User_handle_unique.
    await db.execute(
      "CREATE CONSTRAINT User_handle_unique IF NOT EXISTS FOR (n:`User`) REQUIRE n.`handle` IS UNIQUE",
    );
  },
});
```

When a guard fails, add your own step above it (for example
`SET n.handle = split(n.email, "@")[0]`) and run `cyphra migrate deploy` again.

> Steps run as separate auto-commit statements (Neo4j does not allow schema and data changes in one
> transaction). Generated steps are written to be safe to re-run after a failure (`IF NOT EXISTS`,
> `WHERE … IS NULL`); keep hand-written steps re-runnable too.

## Writing migrations by hand

`cyphra migration:create <name>` creates an empty migration. The `db` handle offers:

- `` db.run`…${value}` ``: a parameterized tagged template.
- `db.execute(text, params?)`: trusted Cypher text, for DDL that cannot be parameterized. It returns rows as plain objects.
- `db.runInTransactionBatches({ inner, batchSize, params })`: wraps `inner` in `CALL { … } IN TRANSACTIONS OF … ROWS` for large rewrites.
- `db.migrate.renameLabel({ from, to })` and `db.migrate.renameProperty({ label, from, to })`.

```js
import { defineMigration } from "cyphra";

export default defineMigration({
  name: "20261120090000_rename-name",
  async up({ db }) {
    await db.migrate.renameProperty({ label: "User", from: "name", to: "displayName" });
  },
});
```

## Tracking

Applied migrations are recorded as `(:__CyphraMigration { name, appliedAt, checksum })`.
`cyphra migrate status` reports migrations that are pending, applied files that were **modified**
after being applied (checksum mismatch), applied migrations whose file is **missing**, and schema
changes not yet captured in a migration. It exits non-zero in all of those cases, so it can gate CI.

## Existing databases

- `cyphra pull` writes a `.cyphra` schema from a live database (see [CLI](/cli)).
- On a project that already used `cyphra push`, the first `migrate dev` re-creates the same constraints
  with `IF NOT EXISTS`, so it is safe to run.
- `cyphra push` still applies constraints and indexes directly, which is handy for prototyping. Prefer
  migrations for anything shared.

Relationship property uniqueness (`@unique` in a `relationship { … }` model) requires Neo4j **5.7+**.
