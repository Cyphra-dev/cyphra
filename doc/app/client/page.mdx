# Typed client

`cyphra generate` turns your `.cyphra` schema into a **fully typed client**: model types, inputs,
filters and results are all inferred from the schema — including nested relations and edge properties.

```bash
pnpm add cyphra
pnpm add -D @cyphra/cli
pnpm cyphra generate   # writes cyphra.gen.ts (path set by "generate" in cyphra.json)
```

```ts
import { createClient } from "./cyphra.gen.js";

const db = createClient({
  uri: process.env.NEO4J_URI!,
  user: process.env.NEO4J_USERNAME!,
  password: process.env.NEO4J_PASSWORD!,
});
```

To reuse a `Driver` your app already has (`neo4j-driver` 5.28+ or 6.x), pass
`createClient({ driver })`; see [Using your own driver](/runtime#using-your-own-driver).

Each node model becomes a delegate with a lower-cased name: `node User` → `db.user`, `node BlogPost` → `db.blogPost`.

> Requires **Neo4j 5.6+** (the client compiles relations to `COLLECT {}` / `EXISTS {}` subqueries).
> [`traverse`](#traversals) needs **Neo4j 5.9+** (quantified path patterns).
> [`findSimilar`](#vector-search) needs **Neo4j 5.15+** (vector indexes; `exact: true` needs 5.18+).
> [`search`](#full-text-search) works on any Neo4j 5 (full-text indexes).

## Reading

```ts
const users = await db.user.findMany({
  where: { email: { endsWith: "@acme.io" }, posts: { some: { published: true } } },
  orderBy: [{ createdAt: "desc" }],
  skip: 0,
  take: 20,
});

const alice = await db.user.findUnique({ where: { email: "alice@acme.io" } }); // User | null
const sure = await db.user.findUniqueOrThrow({ where: { id } }); // throws NotFoundError
const first = await db.post.findFirst({ where: { published: false } });
const total = await db.user.count({ where: { name: { not: null } } });
```

`findUnique`, `update`, `upsert` and `delete` require at least one `@id` / `@unique` field in `where` —
enforced by the types and at runtime.

### select and include

`include` adds relations to all scalar fields; `select` picks exactly what you want. Both nest, and each
relation accepts `where`, `orderBy`, `skip` and `take`. The result type follows your arguments.

```ts
const user = await db.user.findUnique({
  where: { id },
  select: {
    name: true,
    posts: {
      where: { published: true },
      orderBy: { title: "asc" },
      take: 5,
      select: { title: true },
    },
    following: true,
  },
});
// { name: string | null; posts: { title: string }[]; following: (User & { $edge: Follows })[] } | null
```

When a relation's edge is described by a `relationship { … }` model, each related node carries its edge
properties under **`$edge`**.

## Filters

| Field type                                   | Operators                                                       |
| -------------------------------------------- | --------------------------------------------------------------- |
| any scalar                                   | value (equals), `null` (absent), `equals`, `not`, `in`, `notIn` |
| `Int`, `Float`, `String`, `DateTime`, `Date` | `lt`, `lte`, `gt`, `gte` (strings compare lexicographically)    |
| `String`                                     | `contains`, `startsWith`, `endsWith`, `mode`                    |
| lists (`String[]`, …)                        | `has`, `hasEvery`, `hasSome`, `isEmpty`, `equals`               |
| to-many relation                             | `some`, `none`, `every`                                         |
| to-one relation                              | `is`, `isNot`, `null` (no related node)                         |

Combine with `AND`, `OR` and `NOT`.

`mode: "insensitive"` on a `String` filter compares lower-cased values (Cypher `toLower()`) for
`equals`, `not`, `in`, `notIn`, `contains`, `startsWith` and `endsWith`. Range filters (`lt`, `gte`, …)
stay case-sensitive. A property index is not used for these comparisons.

```ts
await db.user.findFirst({ where: { email: { equals: "Alice@Acme.io", mode: "insensitive" } } });
```

## Counting related nodes

`_count` in `include` or `select` adds the number of related nodes per **to-many** relation. Each count
compiles to a `COUNT {}` subquery in the same statement, so no related nodes are loaded.

```ts
const users = await db.user.findMany({
  include: {
    _count: {
      select: {
        posts: { where: { published: true } }, // only count published posts
        followers: true,
      },
    },
  },
});
// (User & { _count: { posts: number; followers: number } })[]
```

- `_count: true` counts every to-many relation of the model.
- Each relation in `_count.select` takes `true` or `{ where }`; the `where` is a normal filter on the
  related node, relation filters included (`{ where: { author: { is: { name: "Alice" } } } }`).
- `_count` also works inside an included or selected relation, at any depth
  (`include: { author: { select: { name: true, _count: { select: { posts: true } } } } }`), and in the
  results of `create`, `update`, `upsert` and `delete`.
- As in Prisma, to-one relations cannot be counted; check them with an `is` / `isNot` filter instead.

To **sort by a relation count**, use `orderBy: { posts: { _count: "desc" } }`. It works at the top level
and inside an included relation, and combines with other sort keys:

```ts
const mostFollowed = await db.user.findMany({
  orderBy: [{ followers: { _count: "desc" } }, { email: "asc" }],
  take: 10,
});
```

## Aggregations

`aggregate` computes `_count`, `_sum`, `_avg`, `_min` and `_max` over the nodes matching `where`, in
one Cypher statement. The result has exactly the aggregates you ask for (same shape as Prisma).

```ts
const stats = await db.post.aggregate({
  where: { published: true },
  _count: true, // or { _all: true, score: true }
  _sum: { views: true },
  _avg: { views: true, score: true },
  _min: { publishedOn: true },
  _max: { views: true, title: true },
});
// {
//   _count: number;
//   _sum: { views: number | null };
//   _avg: { views: number | null; score: number | null };
//   _min: { publishedOn: Date | null };
//   _max: { views: number | null; title: string | null };
// }
```

| Aggregate      | Fields                                       | Result                                         |
| -------------- | -------------------------------------------- | ---------------------------------------------- |
| `_count`       | `true` (nodes), `_all` (nodes), any scalar   | `number` (non-null values for a field)         |
| `_sum`         | `Int`, `Float`                               | `number \| null`                               |
| `_avg`         | `Int`, `Float`                               | `number \| null` (a mean, so not always whole) |
| `_min`, `_max` | `Int`, `Float`, `String`, `DateTime`, `Date` | the field type, or `null`                      |

- `null` values (absent properties) are ignored, as in SQL.
- On an empty match, counts are `0` and every other aggregate is `null` (Cypher's `sum()` returns 0;
  Cyphra returns `null`, like SQL and Prisma).
- `DateTime` and `Date` results come back as `Date` (UTC). Strings compare by code point.
- `orderBy`, `skip` and `take` pick a window of the matching nodes first: `{ orderBy: { views: "desc" }, take: 10, _avg: { views: true } }`
  is the average of the ten most viewed posts.

Asking for an aggregate that does not fit the field (`_sum` on a `String`, `_min` on a `Boolean` or a
list) is a type error, and a `CyphraValidationError` for untyped callers.

## groupBy

`groupBy` groups the matching nodes by one or more fields and aggregates each group, in one statement.
It takes the same `_count`, `_sum`, `_avg`, `_min` and `_max` as `aggregate`, plus `having`, `orderBy`,
`skip` and `take` on the groups.

```ts
const byStatus = await db.post.groupBy({
  by: ["published"], // or a single field: by: "published"
  where: { views: { gt: 0 } },
  _count: { _all: true },
  _avg: { views: true },
  having: { views: { _avg: { gt: 10 } } },
  orderBy: [{ _count: { id: "desc" } }, { published: "asc" }],
  take: 10,
});
// { published: boolean; _count: { _all: number }; _avg: { views: number | null } }[]
```

- **`having`** filters groups. On any scalar field it takes aggregate filters
  (`{ views: { _sum: { gte: 100 } } }`, `{ id: { _count: { gt: 1 } } }`); on a field listed in `by` it
  also takes the usual filters (`{ published: true }`). `AND`, `OR` and `NOT` combine them.
- **`orderBy`** sorts by fields listed in `by` or by aggregates (`{ _max: { views: "desc" } }`,
  `{ _count: { _all: "asc" } }`).
- A `null` key is a group of its own (nodes without the property).

### Grouping by a related node

Fields of a **to-one** relation are written `"relation.field"` in `by`, and come back nested under the
relation name. `having` and `orderBy` use the nested form.

```ts
const perAuthor = await db.post.groupBy({
  by: ["author.name", "author.email"],
  _sum: { views: true },
  having: { author: { name: { not: null } } },
  orderBy: { author: { name: "asc" } },
});
// { author: { name: string | null; email: string | null }; _sum: { views: number | null } }[]
```

Posts without an author fall into the group whose related fields are all `null`. To-many relations
cannot be grouped on (a post would belong to several groups); aggregate from the other side instead,
for example `db.user.groupBy` with `where: { posts: { some: … } }`.

## Traversals

`traverse` follows a relation for several hops and returns the nodes it reaches: "friends of friends",
"everyone downstream of this service", "people within three introductions". It compiles to one Cypher
statement with a [quantified path pattern](https://neo4j.com/docs/cypher-manual/current/patterns/variable-length-patterns/)
(Neo4j 5.9+), with every value sent as a parameter.

```cyphra filename="schema.cyphra"
node User {
  id        String @id @default(cuid())
  email     String @unique
  name      String?
  age       Int?
  following User[] @relationship(type: "FOLLOWS", direction: OUT)
  followers User[] @relationship(type: "FOLLOWS", direction: IN)
}

relationship Follows {
  type "FOLLOWS"
  from User
  to User
  since DateTime @default(now())
}
```

```ts
// Friends of friends: everyone Alice follows, and everyone they follow.
const fof = await db.user.traverse({
  from: { email: "alice@acme.io" },
  via: "following",
  depth: { max: 2 },
  where: { age: { gte: 18 } }, // filter on the reached nodes
  orderBy: { name: "asc" },
  take: 20,
});
// User[]
```

The generated Cypher is:

```cypher
MATCH (s:`User`) WHERE s.`email` = $p0
MATCH (s)((:`User`)-[e0:`FOLLOWS`]->(:`User`)){1,2}(n:`User`)
WHERE (n <> s) AND (n.`age` >= $p1)
WITH DISTINCT n ORDER BY n.`name` ASC LIMIT $p2
RETURN n{.`id`, .`email`, .`name`, .`age`} AS row ORDER BY n.`name` ASC
```

| Argument                  | Meaning                                                                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `from`                    | Start node(s): any `where` filter on the model (`{ id }`, `{ email }`, `{ age: { gt: 30 } }`). Required.                                                 |
| `via`                     | A relation of the model that leads back to the same model (`"following"`), or a list of them (`["following", "followers"]`): each hop takes any of them. |
| `depth`                   | `{ min?, max }` hops. `max` is required; `min` defaults to `1`, and `min: 0` also returns the start node.                                                |
| `direction`               | `"out"`, `"in"` or `"both"`: the arrow direction of every hop. Default: each relation's declared `direction`.                                            |
| `where`                   | Filter on the reached nodes, the same as in `findMany` (relation filters included).                                                                      |
| `edgeWhere`               | Filter on the properties of every edge of the path, typed from the `relationship { … }` model. Only when every relation in `via` has one.                |
| `distinct`                | `true` (default): each reached node once. `false`: one result per path, so a node reached two ways appears twice.                                        |
| `select`, `include`       | Shape the reached nodes, as in `findMany` (`_count` and nested relations included).                                                                      |
| `orderBy`, `skip`, `take` | Sort and page the reached nodes.                                                                                                                         |
| `returnPaths`             | `true`: return `{ node, path }` instead of the node (see [Paths](#paths)).                                                                               |

- **Upper bound.** `depth.max` is required and capped by the client option `maxTraversalDepth`
  (default `10`): `createClient({ uri, user, password, maxTraversalDepth: 4 })`. Every extra hop can
  multiply the number of paths Neo4j explores, so set the cap as low as your queries allow. A missing
  `max`, a `max` above the cap or an unknown relation in `via` is a type error where TypeScript can
  see it, and a `CyphraValidationError` at run time.
- **Cycles.** Neo4j never uses the same relationship twice in one path, so cycles end on their own. A
  path that comes back to its own start node is skipped: Alice is not her own friend of a friend.
- **Same model only.** Each relation in `via` must lead back to the model (`User` to `User`). Chains
  over different models (`User` to `Post` to `Tag`) are not supported yet; use `db.$cypher` for those.
- `traverse` works in [`$transaction`](#transactions) and sees the transaction's own writes.

Edge filters apply to every hop. Only follows made since 2024, both directions, exactly two hops away:

```ts
const recent = await db.user.traverse({
  from: { id: alice.id },
  via: ["following", "followers"], // same as via: "following", direction: "both"
  depth: { min: 2, max: 2 },
  edgeWhere: { since: { gte: new Date("2024-01-01") } },
  select: { email: true, _count: { select: { followers: true } } },
});
// { email: string; _count: { followers: number } }[]
```

### Paths

With `returnPaths: true`, each result is `{ node, path }`. The `path` lists the nodes from the start node
to the reached node and the edges between them, with edge properties typed from the
`relationship { … }` model:

```ts
const rows = await db.user.traverse({
  from: { email: "alice@acme.io" },
  via: "following",
  depth: { max: 3 },
  where: { email: "dave@acme.io" },
  select: { email: true },
  returnPaths: true,
});
const { node, path } = rows[0]!;
node.email; // string
path.nodes.map((u) => u.name); // ["Alice", "Carol", "Dave"]: User scalars
path.edges[0]; // { type: "FOLLOWS", direction: "out", properties: { since: Date } }
```

- `path.edges[i]` joins `path.nodes[i]` and `path.nodes[i + 1]`, and `path.edges.length` is the number
  of hops. `direction` is `"out"` when the edge points from `nodes[i]` to `nodes[i + 1]`, `"in"` when it
  points back (for example when walking `followers`).
- Path nodes carry the model's scalar fields; `select` and `include` shape `node` only.
- With `distinct` (default), `path` is one of the shortest paths to the node. With `distinct: false`,
  every path is its own result.
- The types are exported for your own code: `Path<Node, Edge>`, `PathEdge<Props>`, and
  `ModelPath<CyphraTypeMap, "User", "following">` for the path of a given model and relation.

## Shortest path

`shortestPath` finds one shortest path between two nodes along a relation: "how is Alice connected to
Dave?", "the fewest introductions between two people". `allShortestPaths` returns every path of that
minimal length. Both compile to one Cypher statement with a
[shortest path selector](https://neo4j.com/docs/cypher-manual/current/patterns/shortest-paths/)
(`SHORTEST 1` / `ALL SHORTEST`, **Neo4j 5.21+**), with every value sent as a parameter.

```ts
const path = await db.user.shortestPath({
  from: { email: "alice@acme.io" },
  to: { email: "dave@acme.io" },
  via: "following",
  maxDepth: 4,
});
// ModelPath<CyphraTypeMap, "User", "following"> | null
path?.nodes.map((u) => u.name); // ["Alice", "Carol", "Dave"]
path?.edges[0]; // { type: "FOLLOWS", direction: "out", properties: { since: Date } }
```

The generated Cypher is:

```cypher
MATCH (s:`User`) WHERE s.`email` = $p0
MATCH (t:`User`) WHERE t.`email` = $p1
MATCH p = SHORTEST 1 (s)((:`User`)-[e0:`FOLLOWS`]->(:`User`)){0,4}(t)
WITH p ORDER BY length(p) LIMIT 1
RETURN [n1 IN nodes(p) | n1{.`id`, .`email`, .`name`, .`age`}] AS nodes, {…} AS path
```

| Argument            | Meaning                                                                                                        |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| `from`, `to`        | Start and end node(s): any `where` filter on the model. Both required.                                         |
| `via`               | A relation of the model that leads back to the same model, or a list of them, as in [`traverse`](#traversals). |
| `maxDepth`          | Longest path searched, in hops. Required, and at most the client option `maxTraversalDepth` (default `10`).    |
| `direction`         | `"out"`, `"in"` or `"both"`, as in `traverse`. Default: each relation's declared `direction`.                  |
| `where`             | Filter every intermediate node must match (not the start or end node), relation filters included.              |
| `edgeWhere`         | Filter on the properties of every edge of the path, typed from the `relationship { … }` model.                 |
| `select`, `include` | Shape the nodes of the path, as in `findMany` (`_count` and nested relations included).                        |
| `take`              | `allShortestPaths` only: return at most this many paths.                                                       |

- **Result.** A [path](#paths): `nodes` from the start node to the end node (shaped by `select` /
  `include`, all scalar fields by default) and typed `edges`. `shortestPath` returns `null` when no path
  of at most `maxDepth` hops exists; `allShortestPaths` returns `[]`.
- **Several start or end nodes.** `from` and `to` are filters, so each may match several nodes. Cyphra
  searches every start/end pair and keeps the overall shortest: `shortestPath` returns one path of the
  minimal length (which one, when several tie, is up to Neo4j), and `allShortestPaths` returns every
  path of that length, over all pairs. Use a unique field (`{ id }`, `{ email }`) for a single pair.
- **Same node.** A node that matches both `from` and `to` is joined to itself by a zero-hop path:
  `{ nodes: [node], edges: [] }`.
- **Filters apply during the search.** `where` and `edgeWhere` are checked before the shortest path is
  picked, so when they rule out the shortest path you get the next shortest one, not `null`.
- **Same rules as `traverse`.** `maxDepth` is capped by `maxTraversalDepth`; `via` takes relations that
  lead back to the same model; a missing `maxDepth` or `to`, or a bad relation, is a type error and a
  `CyphraValidationError`. Both methods work in [`$transaction`](#transactions).

Every tied shortest path, through adults only, along follows made since 2024 in either direction:

```ts
const routes = await db.user.allShortestPaths({
  from: { id: alice.id },
  to: { id: dave.id },
  via: "following",
  direction: "both",
  maxDepth: 6,
  where: { age: { gte: 18 } },
  edgeWhere: { since: { gte: new Date("2024-01-01") } },
  select: { name: true },
  take: 10,
});
// { nodes: { name: string | null }[]; edges: PathEdge<{ since: Date }>[] }[]
```

The result type is exported as `ShortestPathResult<CyphraTypeMap, "User", "following", Node>`.

## Vector search

`findSimilar` returns the `k` nodes whose embedding is closest to a query vector, through the
field's [vector index](/schema#vector-fields): the retrieval step of semantic search and GraphRAG.
It is available on models with a `Vector(N) @vectorIndex` field, and `field` only accepts those fields.

```ts
const chunks = await db.chunk.findSimilar({
  field: "embedding",
  vector: await embed("How do I rotate API keys?"), // number[] of length 1536
  k: 5,
  where: { document: { is: { published: true } } },
  include: { document: { select: { title: true, url: true } } },
});
// (Chunk & { document: { title: string; url: string } | null; $score: number })[]
chunks[0].$score; // 0.93
```

Results come best first, shaped by `select` / `include` like `findMany`, each with a `$score`
(model fields cannot start with `$`, so it never collides). `include` is how the graph helps
retrieval: load the chunk's document, its neighbours or its entities in the same statement.

| Argument            | Meaning                                                                                                               |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `field`             | The `Vector(N)` field to search. It must have a `@vectorIndex`.                                                       |
| `vector`            | The query embedding. Its length must be `N`, else `CyphraValidationError` (checked before any query).                 |
| `k`                 | Number of results (a positive integer).                                                                               |
| `where`             | Any filter on the model, relation filters included. See below for how it combines with the index.                     |
| `minScore`          | Drop results that score below this.                                                                                   |
| `candidates`        | Neighbours asked from the index on the first attempt (at least `k`). Default `k`, or `max(10 × k, 100)` with `where`. |
| `maxCandidates`     | Upper bound on the neighbours a filtered search asks for (default: no bound).                                         |
| `exact`             | `true`: skip the index and score every node matching `where` (see below).                                             |
| `select`, `include` | Shape each result, as in `findMany`.                                                                                  |

**Scores** are the index's, in `[0, 1]`, higher is more similar: `(1 + cos) / 2` for `cosine`
(so `0.5` is orthogonal) and `1 / (1 + d²)` for `euclidean`. With Neo4j's default quantization the
index stores compressed vectors, so scores are close to, not exactly, the exact similarity.

**How `where` works.** Without a filter, `findSimilar` is one call to
`db.index.vector.queryNodes(index, k, vector)`. Neo4j 5 vector indexes take no filter: the procedure
returns its nearest neighbours and anything else is applied afterwards, so filtering the top `k`
could leave fewer than `k` results. With `where`, `findSimilar` instead asks the index for
`candidates` neighbours, filters them in the same statement and keeps the best `k`. If fewer than
`k` pass, it asks again for four times as many, until it has `k` results, the index has no more
nodes, the scores fall below `minScore`, or it reaches `maxCandidates`. So you get the `k` best
matching nodes, as far as the approximate index can tell, at the cost of extra queries when the
filter is selective.

**`exact: true`** skips the index: it matches the nodes that pass `where` and ranks them with
`vector.similarity.cosine` / `vector.similarity.euclidean` (Neo4j **5.18+**), in one statement. Use it
when `where` narrows the search to a few thousand nodes (the chunks of one document, one tenant's
data): results are exact and nothing is over-fetched. It also sees nodes written earlier in the same
[`$transaction`](#transactions), which the vector index does not (it only holds committed data).

The generated Cypher for a filtered search, here `where: { document: { is: { published: true } } }`
with `include: { document: { select: { title: true } } }` (`$cyphraCandidates` grows between
attempts):

```cypher
CALL db.index.vector.queryNodes($p3, $cyphraCandidates, $p1) YIELD node, score
WITH collect({n: node, s: score}) AS hits
CALL {
  WITH hits UNWIND hits AS h WITH h.n AS n, h.s AS score
  WHERE EXISTS { MATCH (n)-[:`PART_OF`]->(m0:`Document`) WHERE m0.`published` = $p0 }
  WITH n, score ORDER BY score DESC LIMIT $p2
  RETURN collect({row: n{.`id`, .`text`, .`embedding`,
    `document`: head(COLLECT { MATCH (n)-[r2:`PART_OF`]->(m1:`Document`) RETURN m1{.`title`} })
  }, score: score}) AS rows
}
RETURN size(hits) AS fetched, hits[-1].s AS lowest, rows
```

`findSimilar` works in [`$transaction`](#transactions) and with either driver major. Vectors are
written with a plain `SET` of a float list, which Neo4j indexes like
`db.create.setNodeVectorProperty` would. The `FindSimilarArgs` and `SimilarResult` types are exported.

## Full-text search

`search` runs a full-text query through one of the model's [`@@fulltext` indexes](/schema#full-text-indexes)
and returns the matching nodes, most relevant first: search boxes, autocomplete, keyword search
next to (or combined with) [vector search](#vector-search). It is available on models with a
`@@fulltext` attribute, and `index` only accepts that model's index names.

```ts
const posts = await db.post.search({
  index: "postSearch",
  query: userInput,
  mode: "terms", // treat the input as plain words
  where: { published: true, author: { is: { country: "FR" } } },
  take: 10,
  select: { id: true, title: true, author: { select: { name: true } } },
});
// { id: string; title: string; author: { name: string } | null; $score: number }[]
```

Results are shaped by `select` / `include` like `findMany`, each with a `$score`: Lucene's relevance
score (BM25), positive and unbounded. Scores rank the hits of one query; they are not comparable
across queries or with `findSimilar` scores.

| Argument            | Meaning                                                                                |
| ------------------- | -------------------------------------------------------------------------------------- |
| `index`             | The `@@fulltext` index to query, by name.                                              |
| `query`             | The search text. A blank query returns `[]` without querying.                          |
| `mode`              | `"lucene"` (default), `"terms"` or `"phrase"`: how `query` is read (see below).        |
| `where`             | Any filter on the model, relation filters included, applied to the hits before paging. |
| `minScore`          | Drop hits that score below this.                                                       |
| `skip`, `take`      | Page through the ranked hits, after filtering (default: every hit).                    |
| `select`, `include` | Shape each result, as in `findMany`.                                                   |

**Query syntax.** By default `query` is [Lucene query syntax](https://lucene.apache.org/core/9_11_0/queryparser/org/apache/lucene/queryparser/classic/package-summary.html#package.description),
passed through to Neo4j: `graph databases` (any of the words), `"graph databases"` (the phrase),
`+graph -sql`, `graph AND neo4j`, `title:graph` (one field of the index), `graph*` (prefix),
`grph~` (fuzzy), `title:graph^5 OR body:graph` (boost). Malformed syntax such as `C++ (beta` makes
Neo4j throw. For text typed by users, pick a mode that escapes it:

- `mode: "terms"` escapes the input and matches any of its words, ranked by relevance.
- `mode: "phrase"` escapes the input and matches its words in that order.
- `escapeLucene(text)` (exported) escapes the special characters (`+ - && || ! ( ) { } [ ] ^ " ~ * ? : \ /`)
  and the `AND` / `OR` / `NOT` operators, to mix user input into a query you build:

```ts
import { escapeLucene } from "cyphra";

const prefix = await db.post.search({
  index: "postSearch",
  query: `title:${escapeLucene(input)}*`,
});
const allWords = await db.post.search({
  index: "postSearch",
  query: input
    .split(/\s+/)
    .filter(Boolean)
    .map((w) => `+${escapeLucene(w)}`)
    .join(" "),
});
```

The index's analyzer applies to the query as it does to the text: with `analyzer: "english"`,
`run` finds "running"; with `keyword`, only the exact, case-sensitive value matches.

**How `where` works.** `db.index.fulltext.queryNodes(index, query)` returns every node matching the
query, not a top-k, so filtering afterwards loses nothing: `where` and `minScore` filter the hits in
the same statement, then the rows are ranked by score and `skip` / `take` apply. Without a filter,
`take` is passed to the procedure as `{limit: skip + take}` so Lucene only collects the hits it
returns. The statement for the example above (paged with `take: 10`):

```cypher
CALL db.index.fulltext.queryNodes($p1, $p2) YIELD node, score
WITH node AS n, score WHERE (n.`published` = $p0)
WITH n, score ORDER BY score DESC LIMIT $p3
RETURN n{.`title`, `author`: head(COLLECT {
  MATCH (n)<-[r1:`WROTE`]-(m0:`Author`) RETURN m0{.`name`}
})} AS row, score ORDER BY score DESC
```

`search` works in [`$transaction`](#transactions) and with either driver major. Unlike a vector
index, a full-text index sees the nodes created or changed earlier in the same transaction (unless it
is `eventuallyConsistent`, in which case it only sees committed writes, a moment after commit). The
`SearchArgs`, `SearchMode` and `SearchResult` types are exported.

## Writing

```ts
const alice = await db.user.create({
  data: {
    email: "alice@acme.io",
    posts: { create: [{ title: "Hello graph" }] },
    following: { connect: { email: "bob@acme.io", $edge: { since: new Date() } } },
  },
  include: { posts: true },
});

await db.user.update({
  where: { id: alice.id },
  data: {
    name: "Alice",
    loginCount: { increment: 1 },
    following: { disconnect: { email: "bob@acme.io" } },
  },
});

await db.post.update({ where: { id }, data: { author: { connect: { id: alice.id } } } }); // replaces the edge
await db.post.update({ where: { id }, data: { author: { disconnect: true } } });

await db.user.upsert({ where: { email }, create: { email }, update: { name: "again" } });
await db.user.delete({ where: { id } }); // DETACH DELETE, returns the deleted node
await db.user.createMany({ data: [{ email: "a@x.io" }, { email: "b@x.io" }] });
await db.user.updateMany({ where: { name: null }, data: { name: "anonymous" } });
await db.user.deleteMany({ where: { email: { endsWith: "@spam.io" } } });
```

Relation operations: `create` and `connect` (on create and update), plus `disconnect` and `set`
(to-many only, replaces all edges) on update. On a to-one relation, `connect` / `create` replace the
existing edge.

`connect` is idempotent: it `MERGE`s the relationship, so connecting a pair that is already linked
keeps one edge. When the other side is declared to-one (connecting a post through `user.posts`
while `Post.author` is `User?`), `connect` moves the post: its edge to the previous author is
deleted in the same statement. Many-to-many relations are left alone. On a typed edge, `$edge` and the edge's schema defaults are set when the edge is
created; on an existing edge only the `$edge` properties you pass are updated.

`upsert` is one atomic `MERGE` on the unique key in `where` (`ON CREATE SET` the create data,
`ON MATCH SET` the update), then any nested relation writes of the branch it took. Concurrent
upserts of the same key yield one node as long as the key has a uniqueness constraint, which
`@id` / `@unique` create through `cyphra push` or a migration. See
[Upsert with MERGE](/cypher/upsert-merge#upsert-with-cyphra).

A nested write runs in **one write transaction**: if any step fails (for example a `connect` target
does not exist) nothing is written.

Defaults from the schema are applied on create: `cuid()`, `uuid()`, `now()` and literals
(`@default("draft")`, `@default(0)`, `@default(true)`).

## Transactions

```ts
await db.$transaction(async (tx) => {
  const from = await tx.account.update({ where: { id: a }, data: { balance: { decrement: 10 } } });
  if (from.balance < 0) throw new Error("insufficient funds"); // rolls everything back
  await tx.account.update({ where: { id: b }, data: { balance: { increment: 10 } } });
});
```

The driver may retry the callback on transient errors, so keep it free of outside side effects.

## Raw Cypher

Cypher is never hidden. `db.$cypher` runs a parameterized tagged template and converts values to plain
JS (integers → `number`, temporals → `Date`, nodes → their properties):

```ts
const rows = await db.$cypher<{ name: string; n: number }>`
  MATCH (u:User)-[:AUTHORED]->(p:Post) WHERE p.published = ${true}
  RETURN u.name AS name, count(p) AS n ORDER BY n DESC
`;
```

The low-level [runtime](/runtime) (`db.$client`) and the [query builder](/queries) remain available.
The [Cypher how-tos](/cypher) show common queries (upserts, pagination, counts) both ways.

### DateTime values

Cyphra writes every `DateTime` (including `@default(now())` and the values in `where` filters) at
UTC offset `Z`, whatever the time zone of the server process, and reads it back as a `Date`. The
offset matters in Cypher: `=` and `<` on datetimes take it into account, so the same instant stored
as `2023-12-31T19:00-05:00` is not `=` to `2024-01-01T00:00Z`, and sorts just before it.

Versions before 0.3 used the local offset of the process that wrote the value. If your servers did
not run in UTC, such values still read back as the right `Date` and range filters still work, but
`equals`, `in`, and `lte` / `gte` on that exact instant will not match them. Rewrite them in UTC
once (per label and property):

```cypher
MATCH (n:User) WHERE n.createdAt.offsetSeconds <> 0
SET n.createdAt = datetime({datetime: n.createdAt, timezone: "Z"})
```

## Errors

- `CyphraValidationError`: unknown field or operator, wrong value type, missing required field, or missing unique key.
- `NotFoundError`: `update` / `delete` / `connect` / `findUniqueOrThrow` target not found.
- `CyphraError` (the base class of both): for example an `upsert` whose `where` has extra conditions
  that the existing node does not match.

Field names, labels and relationship types always come from your schema and unknown keys are rejected,
so arguments cannot inject Cypher. Every value is sent as a parameter.
