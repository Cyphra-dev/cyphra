# Native GraphQL API

`native.makeSchema` serves a GraphQL API generated from your `schema.cyphra` and run by the
[typed client](/client): every root field is one client operation (`findMany`, `findUnique`, …),
compiled to one Cypher statement, so filters, ordering, paging, writes and errors behave the same from
TypeScript and from GraphQL. What the API exposes is configured in TypeScript, typed against the
generated client.

<Callout type="warning">
  **Experimental** (see the [stability policy](/stability#experimental-features)): the native API
  may change in a minor release. This release serves **reads** (`findUnique`, `findFirst`,
  `findMany`, `count`, [`aggregate`, `groupBy`](#aggregates-and-groupby), [`search`,
  `findSimilar`](#search-and-findsimilar), [traversals](#traversals)), **writes** (`create`,
  `createMany`, `update`, `updateMany`, `upsert`, `delete`, `deleteMany`, off by default) and
  **[auth](#auth)** (rules compiled into the statement, field rules, `authenticated`), with nested
  `update` / `delete` / `upsert` / `connectOrCreate` and `_count` filters, **[extension
  points](#extend-the-schema)** (computed fields, Cypher-backed fields, custom SDL and resolvers)
  and **[subscriptions](#subscriptions)** (on Neo4j Change Data Capture, off by default)
  ([#77](https://github.com/Cyphra-dev/cyphra/issues/77)). Relay `Node` is opt-in ([below](#relay)).
  To keep the API `@neo4j/graphql` v7 generates, use [`compat.v7`](/graphql); both can be served
  side by side.
</Callout>

## Create the schema

```bash
npm i @cyphra/graphql graphql
```

```ts filename="lib/graphql.ts"
import { native } from "@cyphra/graphql";
import { createClient } from "./cyphra.gen";
import { api } from "./graphql.config";

const db = createClient({ uri, user, password });

export const schema = native.makeSchema({ client: db, config: api });
```

`makeSchema` returns a `GraphQLSchema` with its resolvers: serve it with GraphQL Yoga, Apollo
Server or any GraphQL server.

| Option   | Description                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client` | The client of `cyphra.gen.ts` (possibly `$extends`-ed), or a function of the GraphQL context returning the request's client: `(ctx) => db.$extends(…)`. |
| `schema` | The schema model. Default: `client.$schema`. Required when `client` is a function.                                                                      |
| `config` | The API's configuration, from `defineGraphQL` (below). Default: every read operation of every model, no writes.                                         |
| `debug`  | Show the message of unexpected errors instead of `Internal server error`.                                                                               |

With a function as `client`, every root field runs through that request's client, so the client's
[query hooks](/client#query-hooks) run (multi-tenancy, soft delete, audit logs). Hooks wrap the root
operation only, as in the client.

## Configure it

```ts filename="graphql.config.ts"
import { defineGraphQL } from "@cyphra/graphql/native";
import type { CyphraTypeMap } from "./cyphra.gen";

export const api = defineGraphQL<CyphraTypeMap>({
  models: {
    User: {
      fields: {
        passwordHash: false, // gone from every type and input
        email: { filter: false, sort: false }, // readable, not usable in where / orderBy
      },
    },
    AuditLog: { operations: { read: ["findMany", "count"] } },
    Session: { operations: { read: false } },
    Post: { operations: { create: true, update: true, delete: ["delete"] } },
  },
  naming: { Person: { findMany: "people" } },
  limits: { maxDepth: 4, maxTake: 100, maxAliases: 20, maxComplexity: 10_000 },
});
```

Every key is typed from `CyphraTypeMap`: `{ pasword: false }` or a model that does not exist is a
compile error. `makeSchema` checks the config again at startup (for JavaScript, or configs built
dynamically) and throws a `NativeSchemaError` naming the unknown model, field or option. It
also refuses a model whose create is on while a required field without a default cannot be set
(`fields: { passwordHash: false }` with `create: true`), `create` on an interface and writes on a
union.

| Key                        | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `models.<M>.operations`    | Per group, `true`, `false` or a list of operations: `read` (`findUnique`, `findFirst`, `findMany`, `count`, `aggregate`, `groupBy`, `search`), `traverse` (`findSimilar`, `traverse`, `traversePaths`, `shortestPath`, off by default: the expensive reads), `create` (`create`, `createMany`, `upsert`), `update` (`update`, `updateMany`, `upsert`), `delete` (`delete`, `deleteMany`). `upsert` is served when both `create` and `update` include it. Turning an operation off removes its root field. |
| `models.<M>.fields.<f>`    | `false` hides the field everywhere, writes included. `{ read, filter, sort, create, update }` toggle reading it, filtering and sorting on it, and setting it in create / update inputs (for a relation: its nested writes). `{ read: false, create: true }` is a write-only field. `read` may also be a [field rule](#field-rules). `{ deprecated: "reason" }` emits `@deprecated`. A toggle on an interface applies to its implementations.                                                              |
| `models.<M>.rules`         | Row-level [rules](#rules), compiled into every statement that reaches the model.                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `models.<M>.authenticated` | Operations that need an authenticated request ([`authenticated`](#authenticated)).                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `isAuthenticated`          | `(ctx) => boolean`: whether a request is authenticated. Default: the context has a `user` or a `jwt`.                                                                                                                                                                                                                                                                                                                                                                                                     |
| `defaults.operations`      | The default of every model, per group. Reads are on, `traverse` and writes off.                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `naming.<M>.<operation>`   | A root field name replacing `<model><Operation>` (reads and writes). It is part of the printed contract.                                                                                                                                                                                                                                                                                                                                                                                                  |
| `relay`                    | `true` adds Relay's `Node` interface and `node(id)` ([Relay](#relay)). Off by default.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `traversals.<M>.<field>`   | A [named traversal field](#named-traversal-fields): `{ via: [{ rel, direction?, depth? }, …], args?, description? }`.                                                                                                                                                                                                                                                                                                                                                                                     |
| `limits`                   | Checked before the statement is built (see [Limits](#limits)).                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `mutationTransaction`      | `"field"` (default): each mutation root field is its own transaction. `"request"`: every root field of a mutation operation in one transaction (see [Transactions](#transactions)).                                                                                                                                                                                                                                                                                                                       |
| `generator`                | The generator version the printed SDL follows. Only `1` today.                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## Naming

Root fields are `<model><Operation>`: no pluralization, and the fields of a model sort together.
`node BlogPost` gives `blogPostFindMany` and `blogPostCreate`. Types keep the model names; inputs
are `<Model>Where`, `<Model>WhereUnique`, `<Model>OrderBy`, `<Model>CreateInput`,
`<Model>UpdateInput`; filters are shared per scalar type (`StringFilter`, `IntFilter`,
`DateTimeFilter`, …).

GraphQL names cannot contain `$`, so the client's `$` keys become `_` keys:

| Client                                    | GraphQL                                        |
| ----------------------------------------- | ---------------------------------------------- |
| `db.post.findMany(args)`                  | `postFindMany(...)`                            |
| `select` / `include`                      | the selection set                              |
| `$edge`                                   | `_edge`                                        |
| `$labels`                                 | `_labels`                                      |
| `$on` in `where`                          | `_on`                                          |
| `$on` in `select`                         | inline fragments: `... on Employee { salary }` |
| `__typename` in `where` / `orderBy`       | `_typename`                                    |
| `where: { email: "a@x.io" }` (bare value) | `where: { email: { equals: "a@x.io" } }`       |
| `orderBy: { createdAt: "desc" }`          | `orderBy: [{ createdAt: desc }]`               |
| `data: { views: { increment: 1 } }`       | `data: { _ops: { views: { increment: 1 } } }`  |

A model field named like one of these (`_edge`, `_count`, `_labels`, `_on`, `_typename`, `_score`,
`_scores`, `_ops`) is a `makeSchema` error: rename it in `schema.cyphra`.

## Queries

```graphql
type Query {
  userFindUnique(where: UserWhereUnique!): User
  userFindFirst(where: UserWhere, orderBy: [UserOrderBy!], skip: Int): User
  userFindMany(
    where: UserWhere
    orderBy: [UserOrderBy!]
    skip: Int
    take: Int
    after: String
    before: String
  ): UserList
  userCount(where: UserWhere): Int
}

type UserList {
  nodes: [User!]!
  pageInfo: PageInfo!
  totalCount: Int!
}
```

- `userFindUnique` takes the model's `@id` / `@unique` fields as bare values (and `@@unique`
  keys as objects), plus filters on the other fields. At least one key is required: a `where`
  without one is a `BAD_USER_INPUT` error.
- Root fields are nullable: a failing root field is `null` with its error, and the other root
  fields of the query still return.

### Lists and paging

There is one list query per model, for offset and cursor paging:

```graphql
query Feed($after: String) {
  postFindMany(
    where: { published: { equals: true } }
    orderBy: [{ createdAt: desc }]
    take: 20
    after: $after
  ) {
    nodes {
      id
      title
      author {
        name
      }
    }
    pageInfo {
      hasNextPage
      endCursor
    }
    totalCount
  }
}
```

- `skip` / `take` page by offset; `after` / `before` page by cursor, after or before a
  `pageInfo.endCursor` / `startCursor`. `after` with `skip` skips within the page after the cursor.
- Cursors are **keyset cursors** (the client's [`cursor`](/client#cursor-pagination)): the
  `orderBy` values of the boundary node and its `@id`. A page after a cursor does not shift when
  nodes are inserted before it. A cursor made for another `orderBy` or another model, or a
  malformed one, is a `BAD_USER_INPUT` error, never the first page.
- `pageInfo` loads one row more than `take` to tell whether there is a next page (a previous one
  with `before`). Paging forward, `hasPreviousPage` is `true` when `after` or `skip` is given.
- `totalCount` (the number of nodes matching `where`) is only counted when selected, in the same
  read transaction as the page.

### Filters

`<Model>Where` mirrors the client's `where`:

```graphql
query {
  userFindMany(
    where: {
      OR: [{ role: { equals: ADMIN } }, { email: { endsWith: "@acme.io", mode: insensitive } }]
      posts: { some: { published: { equals: true } } }
      name: null
    }
  ) {
    nodes {
      email
    }
  }
}
```

- Operators are the client's ([table](/client#filters)): `equals`, `not`, `in`, `notIn`, `lt`,
  `lte`, `gt`, `gte`, `contains`, `startsWith`, `endsWith`, `mode: insensitive`; list fields take
  `has`, `hasEvery`, `hasSome`, `isEmpty`, `equals`; points take `distance` and `withinBBox`.
- `name: null` and `{ equals: null }` match nodes without the property; `{ not: null }` the
  others.
- To-many relations take `some`, `none`, `every`; `some: {}` means "has at least one". To-one
  relations take `is`, `isNot`; `author: null` means "has none".
- `_count` filters on the number of related nodes of to-many relations, with the `Int` operators
  and an optional `where` on the counted nodes:
  `userFindMany(where: { _count: { posts: { gte: 2, where: { published: { equals: true } } } } })`.
  Only the nodes the request may read are counted ([rules](#rules)). It compiles to a `COUNT {}`
  subquery (v7's `postsAggregate: { count_GTE: 2 }`).
- `Vector` fields cannot be filtered or sorted on (use the client's `findSimilar`).

### Ordering

`orderBy` is a list with **one key per element** (input object field order is not reliable in
every client library); two keys in one element are a `BAD_USER_INPUT` error.

```graphql
orderBy: [
  { author: { name: asc } } # to-one: a field of the related node
  { tags: { _count: desc, where: { name: { startsWith: "a" } } } } # to-many: their number
  { createdAt: desc }
]
```

Point fields sort by distance: `{ location: { distanceFrom: { longitude: 2.35, latitude: 48.85 } } }`.

### Relations, `_edge` and `_count`

To-many relations take `where`, `orderBy`, `skip` and `take`, as a nested `include` of the client;
to-one relations are nullable objects. The same relation can be loaded twice under aliases, still
in one statement:

```graphql
query {
  userFindUnique(where: { email: "alice@acme.io" }) {
    recent: posts(orderBy: [{ createdAt: desc }], take: 3) {
      title
    }
    popular: posts(orderBy: [{ views: desc }], take: 3) {
      title
    }
    following(orderBy: [{ name: asc }]) {
      name
      _edge {
        since
      }
    }
    _count {
      posts
      followers(where: { role: { equals: ADMIN } })
    }
  }
}
```

- **Edge properties** of a relation with a `relationship { … }` model are the `_edge` field of the
  node it leads to: no connection types. Selecting `_edge` on a node that was not reached through
  such a relation (a root, or another relation) is a `BAD_USER_INPUT` error, not a silent `null`.
  When several relationship models lead to a node, `_edge` is a union of them
  (`union UserEdge = Blocks | Follows`), selected with inline fragments.
- `_count` counts the related nodes of each selected to-many relation (only those), optionally
  filtered. A relation can be counted once per selection.

### Interfaces and unions

Cyphra interfaces (a label shared by their implementations) are GraphQL interfaces; unions are
GraphQL unions. Inline fragments and fragment spreads are the client's `$on`: each implementation's
selection is evaluated only on its nodes, in the same statement.

```graphql
query {
  personFindMany(
    where: { _on: { Employee: { salary: { gt: 100 } }, Customer: {} } }
    orderBy: [{ _typename: asc }, { name: asc }]
  ) {
    nodes {
      __typename
      name
      manager {
        name
      }
      ... on Employee {
        salary
      }
    }
  }
  customers: personCount(where: { _typename: { in: [Customer] } })
}
```

- `_typename` filters and sorts by implementation (an enum of them); `_on` keeps the listed
  implementations matching their own `where`.
- A union has `findFirst`, `findMany` and `count` (no unique key, so no `findUnique`).
- An interface without fields (`interface Archivable {}`) is served as a union of its
  implementations: GraphQL interfaces need at least one field.

### Aggregates and groupBy

`<model>Aggregate` and `<model>GroupBy` are the client's [`aggregate` and
`groupBy`](/client#aggregations): only the selected aggregates are computed, in one
statement.

```graphql
query {
  postAggregate(where: { published: { equals: true } }) {
    _count {
      _all
      rating
    }
    _avg {
      views
    }
    _max {
      createdAt
    }
  }
  postGroupBy(
    by: { fields: [published], author: [name] }
    having: { views: { _sum: { gte: 100 } } }
    orderBy: [{ _sum: { views: desc } }]
    take: 10
  ) {
    published
    author {
      name
    }
    _count {
      _all
    }
    _sum {
      views
    }
  }
}
```

- `_count { _all }` counts nodes, `_count { field }` the field's non-null values. `_sum` keeps the
  field's number type (`Int`, `Float`, `BigInt`), `_avg` is a `Float`, `_min` / `_max` the field's
  type (numbers, strings, enums, ordered temporals). On an empty match counts are `0` and the rest
  `null`.
- `aggregate` takes `where`, and `orderBy` / `skip` / `take` to aggregate over a window of the
  matching nodes.
- `by` lists the model's `fields` and, per to-one relation, its target's fields (the client's
  `"author.name"`); rows nest the same way. Only the fields listed in `by` can be selected on a
  group (`BAD_USER_INPUT` otherwise). Lists, vectors, points and `Json` cannot be grouped on.
- `having` filters groups on aggregates of any field (`{ views: { _avg: { gt: 10 } } }`) and on
  the keys listed in `by` (`{ published: { equals: true } }`); `orderBy` sorts by a key or by an
  aggregate, one key per element. `take` follows [`maxTake`](#limits).
- **Rules apply** as in `findMany`: a node the `read` rules hide is not counted, summed or
  grouped (there is no separate aggregate rule), a row-dependent field rule hides the field's value
  on the rows outside it, and a field a context-only rule denies cannot be aggregated, grouped,
  filtered or sorted on (`FORBIDDEN`).
- A union has neither (its members are aggregated one by one).

### Search and findSimilar

A model with a `@@fulltext` index has `<model>Search`, a model with a `@vectorIndex` field
`<model>FindSimilar`, and a union whose members have them `<union>Search` / `<union>FindSimilar`
(reciprocal rank fusion over the members' indexes), as in the client's
[full-text](/client#full-text-search) and [vector](/client#vector-search) search. The hits are
best first, with their `_score`:

```graphql
query ($vector: [Float!]!) {
  postSearch(index: postSearch, query: "graph databases", mode: terms, take: 10) {
    title
    _score
  }
  chunkFindSimilar(field: embedding, vector: $vector, k: 5, where: { lang: { equals: "en" } }) {
    text
    _score
  }
  searchHitSearch(
    query: "graph"
    mode: terms
    indexes: { Post: postSearch, User: userName }
    where: { _on: { Post: { published: { equals: true } } } }
    take: 20
  ) {
    __typename
    ... on Post {
      title
      _score
      _scores {
        index
        rank
      }
    }
    ... on User {
      name
    }
  }
}
```

- `index` (an enum of the model's `@@fulltext` index names) and `mode` (`lucene`, the default,
  `terms`, `phrase`) are the client's; a blank `query` has no hits. `where` and `minScore` filter
  the hits before `skip` / `take`.
- `findSimilar` takes a vector, so it is **off by default**: turn it on with
  `operations: { traverse: ["findSimilar"] }` (or `traverse: true`). Apps that embed text on the
  server usually expose a custom resolver taking text instead. `field` is an enum of the model's
  vector-indexed fields; `k` follows [`maxTake`](#limits).
- Over a union, `indexes` / `fields` pick the index of each member to query (default: every
  member with exactly one), `where` with `_on` filters per member, and `_scores` lists each index's
  `{ index, score, normalized, rank }`. `rrfK` is the fusion's `k` (default 60).
- `_score` and `_scores` only exist on the hits of these root fields: selecting them anywhere else
  (a `findMany`, a relation) is a `BAD_USER_INPUT` error, not a silent `null`.
- **Rules apply**: a node the `read` rules hide is never a hit, and does not take a neighbour's
  place in `findSimilar` (`k` hits among the readable nodes).

### Traversals

A model with relations back to itself (`User.following`) has `<model>Traverse`,
`<model>TraversePaths` and `<model>ShortestPath`, the client's [`traverse`](/client#traversals)
and [`shortestPath`](/client#shortest-path): one statement each. They are the expensive reads,
**off by default**: turn them on with `operations: { traverse: true }` (or a list).

```graphql
query {
  userTraverse(
    from: { email: { equals: "alice@acme.io" } }
    via: [following]
    depth: { max: 2 }
    where: { name: { not: null } }
    orderBy: [{ name: asc }]
    take: 20
  ) {
    name
  }
  userTraversePaths(from: { id: { equals: "u1" } }, via: [following], depth: { max: 2 }) {
    node {
      name
    }
    path {
      nodes {
        name
      }
      edges {
        type
        direction
        _edge {
          since
        }
      }
    }
  }
  userShortestPath(
    from: { id: { equals: "u1" } }
    to: { id: { equals: "u9" } }
    via: [following, followers]
    maxDepth: 4
  ) {
    nodes {
      name
    }
  }
}
```

- `via` lists relations of the model back to itself (an enum of them), any of them on each hop;
  `direction` overrides their declared direction (`out`, `in`, `both`). `depth: { min, max }` is
  required; `min` defaults to 1, and 0 includes the start node.
- `traverse` returns each reached node once (`distinct: false`: one result per path), filtered by
  `where`, paged by `orderBy` / `skip` / `take` ([`maxTake`](#limits)). `traversePaths` returns
  `{ node, path }`, the shortest path each node was reached by. `shortestPath` returns one shortest
  path between a `from` node and a `to` node, or `null`; its `where` holds on every intermediate
  node.
- Paths are `{ nodes, edges }`: `edges[i]` joins `nodes[i]` and `nodes[i + 1]`, with its `type`,
  `direction` and `_edge` (the relationship model's properties). The nodes of a `shortestPath` take
  any selection; the path nodes of `traversePaths` carry their scalar fields only.
- `depth.max` and `maxDepth` are bounded by `limits.maxTraversalDepth` and by the client's
  `maxTraversalDepth` (default 10), the lower wins.
- **Rules apply to every node of a path**, not only to the start and reached ones: a traversal
  never steps through a node the `read` rules hide (it does not exist for the request), and the
  nodes of a returned path read their fields through the field rules.
- Traversals are served on node models (not on interfaces or unions).

#### Named traversal fields

A traversal across models (`Chunk → Entity → Chunk`) is a field declared in the config, which also
bounds what clients may ask the database to explore:

```ts filename="graphql.config.ts"
export const api = defineGraphQL<CyphraTypeMap>({
  traversals: {
    Chunk: {
      context: {
        via: [
          { rel: "entities" },
          { rel: "related", direction: "both", depth: { min: 0, max: 2 } },
          { rel: "chunks" },
        ],
        args: ["where", "orderBy", "take"], // what clients may pass
      },
    },
  },
});
```

It generates `Chunk.context(where: ChunkWhere, orderBy: [ChunkOrderBy!], take: Int): [Chunk!]!`,
the nodes the hops reach from each chunk (each once, not the chunk itself), compiled into the
parent's statement like a relation load. Each hop follows relations of the model the previous hop
reached; `depth` repeats a hop on a relation back to the same model. `makeSchema` checks the hops,
that their relations are not hidden by `fields`, and that their `depth.max` add up to at most
`limits.maxTraversalDepth` (default 10). The read rules apply to every node of the paths, as above.
Named traversal fields need Neo4j (quantified path patterns in a subquery).

## Mutations

Writes are **off by default**: a model is writable through the API once its config turns them on
(`operations: { create: true, update: true, delete: true }`, or a list per group). Each operation
is one root field of `Mutation`, run as one client operation:

```graphql
type Mutation {
  postCreate(data: PostCreateInput!): Post
  postCreateMany(data: [PostCreateManyInput!]!): PostBatch
  postUpdate(where: PostWhereUnique!, data: PostUpdateInput!): Post
  postUpdateMany(where: PostWhere, data: PostUpdateManyInput!): PostBatch
  postUpsert(where: PostWhereUnique!, create: PostCreateInput!, update: PostUpdateInput!): Post
  postDelete(where: PostWhereUnique!): Post
  postDeleteMany(where: PostWhere): PostBatch
}

type PostBatch {
  count: Int!
  nodes: [Post!]!
}
```

- **Mutations return records**: the created, updated or upserted node, the deleted node as it was.
  Batch mutations return `count` and, when selected, the affected `nodes` (the deleted ones as they
  were), read in the same statement with the client's batch [`select`](/client#writing).
- `createMany` and `updateMany` take scalars only (`<Model>CreateManyInput`,
  `<Model>UpdateManyInput`), as in the client: nested writes go through `create` / `update`.
- Mutation root fields are nullable, like queries: a failing one is `null` with its error.

### Nested writes

Relations in `<Model>CreateInput` take `create`, `connect` and `connectOrCreate`; in
`<Model>UpdateInput` also `disconnect` (a list on to-many, `disconnect: true` on to-one), `set`
(to-many), and [`update`, `delete` and `upsert`](#nested-update-delete-and-upsert):

```graphql
mutation {
  userUpdate(
    where: { id: "u1" }
    data: {
      name: "Alice"
      _ops: { loginCount: { increment: 1 } }
      following: {
        connect: [{ email: "bob@acme.io", _edge: { since: "2026-11-01T00:00:00Z" } }]
        disconnect: [{ email: "carol@acme.io" }]
      }
      posts: { create: [{ title: "Hello", tags: { connect: [{ name: "graphs" }] } }] }
    }
  ) {
    name
    following {
      email
      _edge {
        since
      }
    }
  }
}
```

- **`connect` is a `MERGE`**: connecting a pair that is already linked keeps one edge and updates
  the `_edge` properties given (edge defaults are set only when the edge is created). On a to-one
  relation, `connect` (or `create`) replaces the edge; when the other side is to-one (connecting a
  post through `user.posts` while `Post.author` is `User?`), the post moves. Numeric `_edge`
  properties take `_ops` on `connect` / `set`: `_edge: { _ops: { weight: { increment: 1 } } }`.
- `set` makes the listed nodes the only linked ones (edges to the others are deleted, the listed
  ones are kept or connected).
- Inputs are generated per relation side: a nested create omits the back relation
  (`UserCreateWithoutPostsInput` has no `posts`), and its relation input is named after it
  (`PostCreateManyWithoutAuthorRelation`). Items of a typed edge take `_edge`; `connect` items are
  the target's unique key plus `_edge` (`UserConnectFollows`).
- A model whose `create` is off has **no nested create** either: with `Tag` read-only,
  `PostCreateInput.tags` has `connect` only (no `create`, `connectOrCreate` or `upsert`). The same
  holds for the other writes: nested `update`, `delete` and `upsert` of a model need its
  `update`, `delete` and `upsert` operations.
- Unions take a member-keyed item (`{ Post: { … } }`); an interface is connected by its unique
  key, and created through its implementations.

### Nested update, delete and upsert

On update, a relation also writes the related nodes themselves, in the root field's statement:

```graphql
mutation {
  userUpdate(
    where: { id: "u1" }
    data: {
      posts: {
        update: [
          { where: { id: "p1" }, data: { title: "Edited", _ops: { views: { increment: 1 } } } }
        ]
        delete: [{ id: "p2" }]
        upsert: [
          { where: { id: "p3" }, create: { id: "p3", title: "New" }, update: { title: "Again" } }
        ]
        connectOrCreate: [{ where: { id: "p4" }, create: { id: "p4", title: "Linked or new" } }]
      }
      profile: { upsert: { create: { bio: "Hi" }, update: { bio: "Hello" } } }
    }
  ) {
    posts {
      title
    }
  }
}
```

| Field             | To-many items (`[…]`)                                   | To-one                        | Nothing matches   |
| ----------------- | ------------------------------------------------------- | ----------------------------- | ----------------- |
| `update`          | `<Target>UpdateWhere…Input` `{ where, data }`           | `<Target>UpdateWithout…Input` | `NOT_FOUND`       |
| `delete`          | the target's `WhereUnique`                              | `true`                        | `NOT_FOUND`       |
| `upsert`          | `<Target>UpsertMany…Input` `{ where, create, update }`  | `{ create, update }`          | creates and links |
| `connectOrCreate` | `<Target>ConnectOrCreateMany…Input` `{ where, create }` | `{ where, create }`           | creates and links |

- `update` and `upsert` find **linked** nodes only (on to-many, the one with the unique key of
  `where`); `connectOrCreate` links any node matching `where` (a `MERGE` of the edge, as
  `connect`), and is also served in create inputs. A node with the key that is not linked is not
  taken over by `upsert`: creating it again is `UNIQUE_CONSTRAINT`.
- The data of a nested update is the target's update input without the back relation
  (`PostUpdateWithoutAuthorInput`): plain values, `_ops`, `_labels` and its own nested writes.
- `delete` deletes the node with its `onDelete` rules (`RESTRICTED` when a `Restrict` rule
  refuses).
- On a typed edge, the `_edge` of `create` sets the new edge's properties (on `connectOrCreate`,
  also those of an existing node it links).
- A missing target, a validation issue anywhere in the input or a refused rule fails the root
  field as a whole: nothing it wrote is kept.
- [Rules](#rules) hold: `update` / `delete` rules restrict the targets (outside them: `NOT_FOUND`),
  `create` and `after` rules apply to the nodes `upsert` / `connectOrCreate` create or update.
  A linked node the request may read but not update is `FORBIDDEN` for `upsert` (nothing is
  created instead), and a node it may read but not link is `FORBIDDEN` for `connectOrCreate`.
- Union targets take none of these (write the member); interface targets take `update` and
  `delete`.

### Scalar updates

A field of `<Model>UpdateInput` takes the new value; `null` removes the property (a required field
cannot be `null`: `BAD_USER_INPUT`). Numeric operators go in `_ops`, applied in order:
`_ops: { views: { increment: 1 }, score: { multiply: 2 } }`. Setting a field and an `_ops`
operator on it is a `BAD_USER_INPUT` error. `@min` / `@max` are checked on the value an operator
produces.

### Validation

Validation rules (`@length`, `@min`, `@email`, …) and enum values are checked before anything is
written, as in the client. The error lists every broken rule in `extensions.issues`, with paths in
GraphQL argument terms:

```json
{
  "message": "User.create: 1 value breaks the schema's validation rules: …",
  "extensions": {
    "code": "BAD_USER_INPUT",
    "issues": [
      {
        "path": ["data", "posts", "create", 1, "title"],
        "model": "Post",
        "field": "title",
        "rule": "length",
        "message": "must be at least 3 characters long (got 2)."
      }
    ]
  }
}
```

A rule broken by an `_ops` update has `_ops` in its path (`["data", "_ops", "loginCount"]`).

### Transactions

Each mutation root field is its own transaction (by default), and the fields of one operation run
in order. With `mutationTransaction: "request"`, every root field of a mutation operation runs in
**one write transaction** (one statement each, in order): they commit together or not at all.
The first failing field rolls the whole operation back, the remaining fields are not run, and
every root field is `null` with that field's error (nothing it reported was committed).

## Auth

Authorization is configured in `graphql.config.ts`, next to the operations it guards, as
TypeScript functions of the request's context. Rules are **schema-level and compiled into the
statement**: the same `where` the client compiles is ANDed into every place the model is matched,
so nothing is filtered in JavaScript and no query can read around a rule.

```ts filename="graphql.config.ts"
import { defineGraphQL } from "@cyphra/graphql/native";
import type { CyphraTypeMap } from "./cyphra.gen";

type Ctx = { user?: { id: string; role: "MEMBER" | "ADMIN" } };
const me = (ctx: Ctx) => ctx.user?.id ?? "";

export const api = defineGraphQL<CyphraTypeMap, Ctx>({
  models: {
    User: {
      operations: { update: ["update"] },
      fields: {
        passwordHash: false,
        email: { read: { where: ({ ctx }) => ({ id: me(ctx) }) } }, // each user reads their own
        salary: { read: ({ ctx }) => ctx.user?.role === "ADMIN" }, // admins only
      },
      rules: { update: ({ ctx }) => ({ id: me(ctx) }) },
    },
    Post: {
      operations: { create: true, update: true, delete: true },
      authenticated: { create: true, update: true, delete: true },
      rules: {
        read: ({ ctx }) => ({ OR: [{ published: true }, { author: { is: { id: me(ctx) } } }] }),
        update: ({ ctx }) => ({ author: { is: { id: me(ctx) } } }),
        delete: ({ ctx }) =>
          ctx.user?.role === "ADMIN" ? true : { author: { is: { id: me(ctx) } } },
        after: { create: ({ ctx }) => ({ author: { is: { id: me(ctx) } } }) },
        connect: { tags: () => ({ internal: false }) },
      },
    },
    AuditLog: { rules: { read: () => false } },
  },
});
```

### Authentication

`makeSchema` does not verify tokens: the server's context function does, and `Ctx` types what
rules see. `native.jwtContext` builds such a context from the `Authorization: Bearer <jwt>` header,
with the same verifier as `compat.v7`'s `features.authorization`, so both APIs can share one
context function:

```ts filename="app/api/graphql/route.ts"
import { createYoga } from "graphql-yoga";
import { native } from "@cyphra/graphql";

const yoga = createYoga({
  schema,
  context: native.context(
    schema,
    native.jwtContext({
      key: process.env.JWT_SECRET!, // or { url: "https://…/.well-known/jwks.json" }
      verifyOptions: { issuer: "https://auth.example.com", audience: "api" },
      user: (jwt) => ({ id: jwt.sub!, role: jwt.role as "MEMBER" | "ADMIN" }),
    }),
  ),
});
```

- The context is `{ token, jwt, user }`: `jwt` is the verified payload, `user` what the `user`
  option makes of it. A missing, malformed, expired or forged token leaves the request anonymous
  (no `jwt`, no `user`), as in `compat.v7`. It reads `{ request }` (GraphQL Yoga, Fetch servers) or
  `{ req }` (Apollo Server on Node).
- Any context function works: `context: async ({ request }) => ({ user: await verify(request) })`.
- `native.context(schema, build)` (optional) also sets [`ctx.cyphra`](#ctxcyphra) before any
  resolver runs.

### `authenticated`

`models.<M>.authenticated` names the operations that need an authenticated request: `true` (all of
them) or per group, like `operations` (`{ create: true, update: ["update"] }`). An anonymous request
gets `UNAUTHENTICATED` before anything runs. A request is authenticated when
`config.isAuthenticated(ctx)` says so (default: the context has a `user` or a `jwt`).

A whole group (`read: true`, `create: true`, …) also applies wherever the model is reached: for an
anonymous request, the model's nodes are not there in relations, `_count` and relation filters
(`read`), and nested writes cannot create or update them. A list of operations guards only those
root fields.

### Rules

A rule is a function of `{ ctx }` returning `true` (allowed), `false` (denied) or a `where` on the
model, typed as the client's `where` of that model:

| Rule                       | Applies to                                                                                                                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `read`                     | Every read of the model: root fields, relation loads at any depth, relation filters (`some` / `none` / `every` / `is`), `_count`, `totalCount`, mutation results, and the targets of writes. |
| `create`                   | `({ ctx, data }) => boolean`: each node created, root or nested, from its create data, before anything runs.                                                                                 |
| `update`                   | The nodes `update` / `updateMany` / `upsert` match, whatever they write (scalars, relations only, or nothing), and the targets of nested `update` / `upsert`.                                |
| `delete`                   | The nodes `delete` / `deleteMany` match, and the targets of nested `delete`.                                                                                                                 |
| `connect.<relation>`       | The targets a nested `connect` / `set` may link (a `where` on the target model).                                                                                                             |
| `disconnect.<relation>`    | The targets a nested `disconnect` / `set` may unlink.                                                                                                                                        |
| `after.create` / `.update` | Checked on the nodes created / updated once every write of the statement ran (nested ones included); a node that does not match rolls the whole write back.                                  |

- **Compiled, not filtered in JavaScript.** A `where` rule is the client's `where`: relations,
  `_on`, `_labels`, anything a filter can do. Context values are parameters. A rule's own `where`
  is not subject to other rules.
- **Evaluated once per request**, against its context, and shared by its root fields.
- **Denied vs not found.** An `update` / `delete` / `connect` on a node outside its rules fails
  with `NOT_FOUND`: the node does not exist for this request, so a rule never reveals that a key
  exists. A node the request cannot `read` cannot be updated, deleted, connected or disconnected
  either. `false` (the whole operation denied) fails the root field with `FORBIDDEN`; a failing
  `create` or `after` rule is `FORBIDDEN` too, and nothing is written.
- **Relationships.** Connecting a node whose other side is to-one (`user.posts.connect` moves a
  post from its author) is an update of that node: its `update` rule applies. A to-one edge a
  write must replace (`connect` or `create` on `post.author`) is a disconnect of the current target:
  outside the `disconnect` rule, the write is `FORBIDDEN`. Explicit `disconnect` / `set` leave the
  edges outside the rule alone.
- **Mutation results** apply `read`: relations of the written node show what the request can
  read, field rules apply, and a written node the request cannot read is returned as `null` (the
  write happened). Batch `nodes` leave such nodes out.
- **Interfaces and unions.** A rule on an interface applies to every implementation; a node
  matched through an interface or a union gets its own model's rules too.
- **Startup check.** Rule keys, models and relations are typed from `CyphraTypeMap`, and
  `makeSchema` checks them again. It also calls every `where` rule once with an empty context
  (`{ ctx: {} }`) and checks the fields and relations of the `where` it returns, so
  `{ publishd: true }` fails at startup even in JavaScript. A rule that throws without a context is
  checked on its first request (an invalid `where` then fails that request with
  `INTERNAL_SERVER_ERROR`).

<Callout type="info">
  TypeScript checks object literals returned by a function only partly: `({ publishd: true })` and
  `({ author: { is: { emial: "x" } } })` fail `tsc`, but a misspelled key next to a correct one
  (`({ published: true, publishd: true })`) does not. The startup check catches it.
</Callout>

On FalkorDB, which cannot roll a write back, `after` rules and `disconnect` rules are refused.

### Field rules

`fields.<f>.read` takes a rule instead of a boolean. A field with a rule is generated nullable.

- **Context-only**: `read: ({ ctx }) => boolean`, evaluated once per request. A denied field
  selected is `null` with a `FORBIDDEN` error at its path (`extensions.field` names it); using it
  in `where`, `orderBy` (also through a relation) or `_count` fails the root field with
  `FORBIDDEN` before anything runs.
- **Row-dependent**: `read: { where: ({ ctx }) => … }`, compiled to
  `CASE WHEN <where> THEN n.email END`. The field is `null` on the rows the `where` does not
  match, and filters, ordering, unique lookups and mutation results see that `null` too: no query
  can probe the hidden values. Scalar fields only; not the `@id` field.

A rule on a field of an interface goes on the interface and applies to every implementation.

### `ctx.cyphra`

`ctx.cyphra` is the request's client **with the API's rules applied** (the same rules as the
generated root fields), for custom resolvers and anything else that reads on the request's
behalf; `ctx.cyphra.$unsafe` is the client without them, for the rare code that must.

```ts
const yoga = createYoga({ schema, context: native.context(schema, native.jwtContext({ key })) });

// In a resolver:
const drafts = await ctx.cyphra.post.findMany({ where: { published: false } }); // only readable ones
const all = await ctx.cyphra.$unsafe.post.count(); // no rules
```

`native.context(schema, build)` sets it before any resolver runs. Without it, the first generated
root field of the request sets it, when the context has no `cyphra` of its own; the resolvers of
[`extend`](#custom-root-fields-and-types) always have it. `ctx.cyphra.selection(info)` turns the
GraphQL selection into the client's `select` ([below](#ctxcyphraselectioninfo)).

### Hooks

Rules are declarative and reach every place a model appears in a statement. [Query
hooks](/client#query-hooks) (a `client` function: `(ctx) => db.$extends(…)`) are code around one
**root** operation: they do not run for `post` loaded under `user { posts }`. Use a rule for
anything that must hold wherever a model is reached, and hooks for the rest (hashing a password,
audit logs, soft delete).

## Security guide

Checklist for an API exposed to untrusted clients:

1. **Expose on purpose.** Writes are off by default; turn on the operations each model needs, per
   group or per operation. Hide fields no client should see with `fields: { f: false }`.
2. **Guard data with rules, not with toggles.** `operations: { read: false }` removes root fields
   only: the model is still reached through relations. `rules: { read }` hides its nodes
   everywhere.
3. **Write `update` / `delete` rules** for every writable model, and `after.create` (or a
   `create` rule) to constrain what a create may produce, such as the author being the requester.
4. **Guard relationships.** `connect` / `disconnect` rules restrict what nested writes may link;
   remember that connecting through a to-many side can move a node off its to-one owner (its
   `update` rule applies).
5. **Use field rules for sensitive values** (emails, salaries): they cannot be filtered, sorted or
   looked up by unique key around the rule.
6. **Use `ctx.cyphra`** in custom resolvers, so they apply the same rules; keep `$unsafe` for
   code that must bypass them, and review it.
7. **Review Cypher-backed fields like raw queries.** Rules do not apply inside their Cypher (the
   nodes they return are filtered by their read rules). Pass the context and arguments as
   interpolated values (parameters), never build the text from them.
8. **Set [limits](#limits)** (`maxDepth`, `maxTake`, `maxComplexity`) to bound what one request may
   load, and leave `debug` off in production.
9. **Commit the printed contract** ([`cyphra graphql print --check`](#print-and-check-the-contract))
   so a change in what the API exposes shows up in review.

What the native API fixes over `@neo4j/graphql` v7 (each has a test in
`packages/graphql/test/native.auth.integration.test.ts` and the `auth` fixture of the compat
suite):

| v7                                                                                             | Native API                                                                                        |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `@mutation(operations: [])` hides root mutations; a nested `create` through another type works | A model whose writes are off has no nested create; a `create` rule holds through nested writes.   |
| `@query(read: false)` types are readable through relationships                                 | A `read` rule hides the nodes in relations, `_count`, relation filters and connects.              |
| `where` / `sort` / aggregation filters can probe fields and nodes the user cannot read         | Filters and sorting only see readable nodes, and ruled fields as `null` (or `FORBIDDEN`).         |
| `AGGREGATE` rules are separate from `READ` rules                                               | One `read` rule covers counts, `totalCount`, `_count`, aggregates, groups and search hits.        |
| Relationship-only updates skip the node's `UPDATE` rules                                       | `update` restricts every update, whatever it writes; connects that move a node need its `update`. |
| `create` responses ignore `READ` rules                                                         | Mutation results apply `read` and field rules.                                                    |
| Rules are strings in SDL directives, checked when the schema is built                          | Rules are TypeScript, typed against `schema.cyphra`, and checked again at startup.                |

## Extend the schema

A real API does not live on generated CRUD alone. Four extension points add to the generated
schema, all part of the [printed contract](#print-and-check-the-contract):

| You need                                         | Use                                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| A field computed in TypeScript from other fields | [`computed`](#computed-fields), from the client's `$extends({ result })` |
| A field computed by Cypher (v7 `@cypher`)        | [`cypherFields`](#cypher-backed-fields)                                  |
| Dashboard queries, business mutations, own types | [`extend`](#custom-root-fields-and-types): SDL plus resolvers            |
| A custom resolver returning generated types      | [`ctx.cyphra.selection(info)`](#ctxcyphraselectioninfo)                  |

### Computed fields

A computed field of the client (`$extends({ result })`) is exposed by naming its GraphQL type (the
client knows its TypeScript type, not its GraphQL one):

```ts filename="server.ts"
const db = createClient({ uri, user, password }).$extends({
  result: {
    user: {
      fullName: {
        needs: { firstName: true, lastName: true },
        compute: (u) => `${u.firstName} ${u.lastName}`,
      },
    },
  },
});

const api = defineGraphQL<CyphraTypeMap, Ctx>({
  computed: {
    User: {
      fullName: "String!",
      // or { type, read: ({ ctx }) => boolean, description, deprecated }
    },
  },
});
export const schema = native.makeSchema({ client: db, config: api });
```

`User.fullName: String!` is in the schema. When a query selects it, its `needs` are added to the
statement's projection and `compute` runs on each row after decoding, as in the client, also on
nodes loaded through relations. It cannot be filtered or sorted on (it is not in the database).
`makeSchema` checks that the client declares each computed field (for a `client` function, on its
first request). The GraphQL type is not checked against `compute`'s return type. `needs` are read
through the request's rules: a field a field rule hides from the request is `null` in `compute`.

### Cypher-backed fields

The native `@cypher`: a Cypher expression evaluated on each node, compiled into the parent's
statement (still one statement), built with the `cypher` tag of `@cyphra/graphql`:

```ts filename="graphql.config.ts"
import { defineGraphQL, native } from "@cyphra/graphql";
const { cypher } = native;

export const api = defineGraphQL<CyphraTypeMap, Ctx>({
  cypherFields: {
    User: {
      followerCount: {
        type: "Int!",
        cypher: ({ node }) => cypher`COUNT { (${node})<-[:FOLLOWS]-() }`,
      },
      followersSince: {
        type: "Int!",
        args: { since: "DateTime!" },
        cypher: ({ node, args }) =>
          cypher`COUNT { (${node})<-[f:FOLLOWS]-() WHERE f.since >= ${args.since} }`,
      },
      recommended: {
        type: "[Movie!]!",
        args: { first: { type: "Int", default: 5 } },
        cypher: ({ node, args, ctx }) => cypher`
          [(${node})-[:WATCHED]->(:Movie)<-[:WATCHED]-(:User)-[:WATCHED]->(m:Movie)
            WHERE m.region = ${ctx.region} | m][0..${args.first}]`,
      },
    },
  },
});
```

- **The expression.** It is a Cypher expression (wrap a full subquery in `COUNT {}`, `COLLECT {}`
  or a list comprehension). `node` is the variable of the node it is evaluated on.
- **Values are parameters.** Every `${…}` other than `node` (an argument, a context value, a
  constant) is bound as a parameter, never spliced into the text: a hostile `ctx` or argument
  value cannot change the statement. `args` arrive encoded for their declared type (`Int` as a
  Cypher integer, so `[0..${args.first}]` works; `DateTime` as a date-time). Nested `cypher` fragments
  are inlined with the same rules.
- **Types.** `type` is a scalar or an enum (`"Int!"`, `"[String!]!"`), decoded like a property of
  that type, or a model (`"Movie"`, `"[Movie!]!"`): the expression returns a node or a list of
  nodes, and the field takes a selection like a relation (fields, relations, `_count`, computed
  fields, other Cypher fields). Arguments are scalars or enums.
- **Filters and sorting.** A field returning one comparable scalar (`String`, `Int`, `Float`,
  `Boolean`, temporal, `BigInt`, an enum) without arguments is in `<Model>Where` and (except a
  `Boolean`) in `<Model>OrderBy`: `where: { followerCount: { gte: 10 } }`,
  `orderBy: [{ followerCount: desc }]`. `filter: false` / `sort: false` turn that off.
- **`read`**: a context-only rule, as for [field rules](#field-rules): a denied field is `null`
  with `FORBIDDEN`, and cannot be filtered or sorted on.

<Callout type="warning">
  **Rules do not apply inside the Cypher of a Cypher-backed field**: it is raw Cypher, and it
  reads whatever it matches: `COUNT { (${node})<-[:FOLLOWS]-() }` counts hidden followers too.
  When the expression returns nodes, those nodes are filtered by the target's read rules (and
  their fields by field rules), but anything the expression aggregates, compares or counts is not
  (a `LIMIT` or a slice in the expression applies before the rules, so it may return fewer nodes).
  Write rule-sensitive logic in the expression itself (with the context as a parameter), or use a
  computed field or a custom resolver on `ctx.cyphra`.
</Callout>

Cypher-backed fields are declared on node models (not interfaces or unions). On FalkorDB, a
Cypher-backed field returning nodes throws `UnsupportedFeatureError` (scalars work); the
expression is written in the Cypher of your database.

### Custom root fields and types

`extend` merges SDL and resolvers into the generated schema: new types (non-node result types),
root fields (`extend type Query` / `extend type Mutation`), and fields added to generated types.

```ts filename="graphql.config.ts"
export const api = defineGraphQL<CyphraTypeMap, Ctx>({
  extend: {
    typeDefs: /* GraphQL */ `
      type DashboardStats {
        postsThisWeek: Int!
        topAuthors: [User!]!
      }
      extend type Query {
        dashboard: DashboardStats!
        semanticSearch(text: String!, take: Int = 10): [Chunk!]!
      }
      extend type Mutation {
        publishPost(id: ID!): Post
      }
      extend type User {
        greeting: String!
      }
    `,
    resolvers: {
      Query: {
        dashboard: () => ({}), // its fields below
        semanticSearch: async (_, { text, take }, ctx, info) =>
          ctx.cyphra.chunk.findSimilar({
            field: "embedding",
            vector: await embed(text),
            k: take,
            ...ctx.cyphra.selection(info),
          }),
      },
      DashboardStats: {
        postsThisWeek: (_, __, ctx) =>
          ctx.cyphra.post.count({ where: { createdAt: { gte: weekAgo() } } }),
        topAuthors: (_, __, ctx, info) =>
          ctx.cyphra.user.findMany({
            orderBy: [{ posts: { _count: "desc" } }],
            take: 5,
            ...ctx.cyphra.selection(info),
          }),
      },
      Mutation: {
        publishPost: (_, { id }, ctx, info) =>
          ctx.cyphra.post.update({
            where: { id },
            data: { published: true },
            ...ctx.cyphra.selection(info),
          }),
      },
      User: {
        // A field added to a generated type: its parent is the node, with its id and `needs`.
        greeting: { needs: { name: true }, resolve: (user) => `Hello, ${user.name}!` },
      },
    },
  },
});
```

- **Checked at startup.** The SDL is validated against the generated schema: an `extend type
User` field colliding with a generated one (a scalar, a relation, a computed or Cypher-backed
  field) is an error, so is a resolver for a generated field or for a field the SDL does not
  declare. A field added to a generated type needs a resolver. `extend type Mutation` works when
  no generated mutation is on (it becomes the `Mutation` type), and `extend type Query` works
  when every generated read is off (`defaults: { operations: { read: false } }`): an API may
  serve only custom root fields. The API needs at least one `Query` field, generated or added.
- **`ctx.cyphra` is the request's client with the rules applied**, so a custom resolver cannot read
  around a rule by accident; an `update` through it on a node outside the `update` rule is
  `NOT_FOUND`, as from a generated field. `ctx.cyphra.$unsafe` is the raw client.
- **Non-node types are ordinary GraphQL**: their resolvers run as GraphQL runs them. Each one that
  calls the client is one statement; use DataLoader if a list of them is resolved.
- **Errors** of the client are mapped as for generated fields (`NOT_FOUND`, `BAD_USER_INPUT`, …);
  a `GraphQLError` you throw is returned as is.

### `ctx.cyphra.selection(info)`

`ctx.cyphra.selection(info)` turns the selection of the field being resolved, when it returns a
generated type (a model, or a list of one), into the client's `select`: aliases, fragments,
relations with their arguments (and `_edge` on them), `_count`, computed and Cypher-backed fields, with the
request's field rules. Spread it into the client call and return the result as is: the resolver
loads exactly what was asked in **one statement** (no N+1 for nested fields), and the result is
shaped like a generated field's. Selecting `_score` works on the results of `findSimilar` /
`search`. On a field that does not return a generated type, it throws `BAD_USER_INPUT`.

## Scalars

| Cyphra                                           | GraphQL                                                              |
| ------------------------------------------------ | -------------------------------------------------------------------- |
| `String` with `@id`                              | `ID`                                                                 |
| `String`, `Int`, `Float`, `Boolean`              | the same (`Int` is GraphQL's 32-bit `Int`: use `BigInt` above it)    |
| `DateTime`                                       | `DateTime` (ISO 8601: `2026-11-01T09:30:00.000Z`)                    |
| `Date`                                           | `Date` (`yyyy-mm-dd`)                                                |

| `BigInt`                                         | `BigInt` (a decimal string)                                          |
| `Json`                                           | `Json` (any JSON value)                                              |
| `Point`, `CartesianPoint`                        | objects (`{ longitude latitude height }`, `{ x y z }`), `PointInput` |
| `Vector(N)`                                      | `[Float!]`                                                           |

## Limits

`config.limits` bounds what one root field may ask the database to load. Each is checked before
the statement is built; exceeding one fails the root field with `BAD_USER_INPUT` and
`extensions.limit` naming it.

| Limit               | Description                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `maxDepth`          | Deepest relation nesting (a root's relations are depth 1).                                                                           |
| `maxTake`           | Largest `take` of a list, root or relation (and of `groupBy`, `search`, `findSimilar`'s `k`); also the `take` of one that sets none. |
| `maxAliases`        | Most aliased fields in one root field's selection.                                                                                   |
| `maxComplexity`     | Most rows a root field may load: each list multiplies its parent's rows by its `take` (`maxTake`, or 100, when it has none).         |
| `maxTraversalDepth` | Largest `depth.max` of a traversal and `maxDepth` of a shortest path; also bounds named traversal fields at startup.                 |

| ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------- | --------------------------------------------------------------------- |

| anything else (driver, bug)                                                                                                        | `INTERNAL_SERVER_ERROR` | message masked unless `debug: true`                                   |

## Relay

`relay: true` in the config adds Relay's `Node` interface and a `node(id: ID!)` root field:

```graphql
interface Node {
  id: ID!
}

type Post implements Node {
  id: ID! # the global id
  rawId: ID! # the post's own id field
  title: String!
}

type Query {
  node(id: ID!): Node
}
```

- Every model with an `@id` field of type `String`, `Int` or `BigInt` implements `Node` (an
  interface with one implements it too). Its global id is `base64("<Type>:<id>")`;
  `native.toGlobalId` / `native.fromGlobalId` build and read them on the server.
- The model's own field named `id` is returned as `rawId`, since `id` is the global id. Inputs
  (`where`, `orderBy`, `<model>FindUnique`) keep `id` with raw values. A model with a field already
  named `rawId` is a `makeSchema` error.
- `node(id)` is one `findUnique`. It returns `null` for an id of an unknown type, of a model whose
  reads are all off, or of a node that does not exist; a string that is not a global id is a
  `BAD_USER_INPUT` error.

Relay is off by default.

## Subscriptions

<Callout type="warning">
  **Experimental** (see the [stability policy](/stability#experimental-features)): subscriptions of
  the native API may change in a minor release. They need Neo4j **Change Data Capture**: Neo4j
  Enterprise Edition or Aura, with the database in CDC mode (`ALTER DATABASE neo4j SET OPTION
  txLogEnrichment 'FULL'`).
</Callout>

`operations: { subscribe: true }` adds `Subscription` root fields for a model (off by default;
`defaults.operations.subscribe` turns them on for every model):

```graphql
type Subscription {
  postChanged(where: PostWhere, operations: [ChangeOperation!]): PostChange!
  # One pair per readable relation of the model:
  postTagsConnected(where: PostWhere, relatedWhere: TagWhere): PostTagsEvent!
  postTagsDisconnected(where: PostWhere, relatedWhere: TagWhere): PostTagsEvent!
}

type PostChange {
  operation: ChangeOperation! # CREATED, UPDATED, DELETED
  id: ID! # the key of the node, also for DELETED (the global id with relay)
  node: Post # re-read with the selection and the read rules; null for DELETED
  changedFields: [String!]! # UPDATED: the fields whose value changed
}

type PostTagsEvent {
  id: ID! # the post's key
  relatedId: ID! # the tag's key
  node: Post!
  related: Tag!
  # _edge: the relationship's properties, when the relation has a relationship model
}
```

`subscribe` takes `changed`, `connected` and `disconnected` (`subscribe: ["changed"]` for node
changes only). `config.naming.<Model>.changed` renames `<model>Changed`, and
`authenticated: { subscribe: true }` requires an authenticated subscriber. Subscriptions are
served on node models with an `@id` field (`String`, `Int` or `BigInt`), not on interfaces or
unions; a relation has events when its target has one too.

Serve them with a `native.CDCReader`, one per server, closed on shutdown:

```ts filename="graphql.ts"
import { native } from "@cyphra/graphql";

export const cdc = new native.CDCReader({ client: db, pollInterval: 500 });
export const schema = native.makeSchema({ client: db, config: api, subscriptions: cdc });

// On shutdown: stops polling and ends the open subscriptions.
cdc.close();
```

The reader takes `client` (a Cyphra client) or `driver` (`neo4j-driver`, with `database`), polls
the change log (`db.cdc.query`) only while a subscription is open, starting from the position when
the first one opens, and serves every subscription of the process. Events include writes made
outside the GraphQL API. Hosting is as for [`compat.v7` subscriptions](/graphql#hosting): a
long-running process, not serverless functions. Without CDC, subscribing fails with
`CDC_UNAVAILABLE`.

### Rules apply to every event

The rules are evaluated once, with the context the subscription opened with (`context.jwt`, from
`native.jwtContext` for example). For each batch of changes, every subscription **re-reads** its
nodes on its client, in one statement (`findMany` by key with its `where` and the API's rules,
with exactly its selection), so:

- an event is delivered only if the subscriber may read the node **now**: a draft another user
  creates, or a node that does not match `where`, is not delivered; once published, its next
  update is. `node` and its relations are what a query would return at that moment;
- a relationship event is delivered only if the subscriber may read **both** nodes (`where` on the
  node, `relatedWhere` on the related one): a readable post tagged with a hidden tag is not
  delivered, nor is a user's `posts` event for a post the rules hide;
- `changedFields` leaves out fields a field rule hides from the subscriber (context or
  row-dependent) and fields the config hides;
- `DELETED` carries only the key (the node is gone; its old properties would bypass the rules). It
  is delivered for every deleted node when the subscriber reads every node of the model (no
  `where`, no read rule restricting the model, and `client` is not a function of the context),
  and otherwise only for nodes the subscription delivered before: the key of a node the subscriber
  could not read is never sent;
- `…Disconnected` is delivered while both nodes exist (when a node is deleted with its
  relationships, `<model>Changed` reports it); `_edge` holds the properties the relationship had.

Several changes to one node in one batch are each delivered, re-read once: they show the node as
it is when the batch is read. Updates of relationship properties are not events.

## Print and check the contract

The generated SDL is deterministic: printed with `lexicographicSortSchema` and `printSchema`,
descriptions included. Commit it and check it in CI, so a field removed by a schema edit or a
config toggle shows up in review:

```bash
cyphra graphql print --out schema.graphql   # write it (reads graphql.config.ts)
cyphra graphql print --check                # fails when schema.graphql is out of date
```

`--check` lists the breaking and dangerous changes between the committed SDL and the generated one
([CLI reference](/cli#print-the-native-graphql-contract)). From code, `native.printSchema(schemaModel,
config)` returns the same text. `config.generator` pins the generator version: a release that
would print something else for the same schema and config ships it as a new, opt-in version.

## One statement per root field

A root field's arguments and its whole selection (fragments resolved, `@skip` / `@include`
applied, variables substituted) are translated into one client operation, which compiles one
Cypher statement (`COLLECT {}` / `COUNT {}` subqueries for relations, `CASE WHEN n:Label` for
fragments). Nested fields do no I/O: a query runs as many statements as it has root fields,
whatever its depth. A `findMany` that selects `totalCount` with its nodes runs the page and the
count in one read transaction. A mutation root field (nested writes and the returned record
included) is one write statement too.

## Side by side with compat.v7

The two APIs have types with the same names and different shapes, so they are served on separate
endpoints, from the same client or driver and the same graph:

```ts filename="app/api/graphql/[[...v]]/route.ts"
const v7 = compat.v7.makeSchema({ typeDefs, client: db.$client });
const v2 = native.makeSchema({ client: db, config: api });
// /api/graphql stays the v7 API; /api/graphql/v2 is the native one.
```

Frontends move operation by operation. The [migration guide](/guides/migrate-from-neo4j-graphql#next-the-native-api)
covers the steps; the tools are:

- `cyphra graphql migrate-operations` rewrites v7 operations (`.graphql` files, `gql` / `graphql`
  templates) into native ones, following the table below, and reports what it cannot translate
  ([CLI](/cli#migrate-operations-to-the-native-api)).
- `cyphra graphql compare` runs each v7 operation on `compat.v7` and its translation on the native
  API, maps the v7 result to the native shape and reports the differences
  ([CLI](/cli#compare-compatv7-and-the-native-api)).
- `cyphra graphql migrate-rules` drafts `rules` and `authenticated` from `@authorization` /
  `@authentication`, as TypeScript to review ([CLI](/cli#draft-native-rules-from-authorization)).

The same functions are exported as `migrate.translateDocument`, `migrate.compareResults` and
`migrate.draftRules` (experimental), with `migrate.createMigrationContext({ typeDefs, schema,
config })`.

## Mapping from compat.v7

Every construct `compat.v7` serves, and its native equivalent. "No equivalent" means the codemod
leaves the operation as it is, with a `# cyphra: not translated: …` comment saying why; a
selected field it drops gets a `# cyphra: …` note instead. Never silently: a filter left out would
widen the result.

### Queries

| v7 (`compat.v7`)                                                                           | Native                                                                                                          |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `movies(where, sort, limit, offset)`                                                       | `movieFindMany(where, orderBy, take, skip) { nodes }`                                                           |
| `limit: 0` (v7 ignores it)                                                                 | dropped (`take: 0` returns no node)                                                                             |
| `moviesConnection(first, after, sort, where) { totalCount edges { node } pageInfo }`       | `movieFindMany(take, after, orderBy, where) { nodes totalCount pageInfo }`                                      |
| `edges { cursor }`, a v7 cursor stored by a client                                         | no equivalent: cursors are per page (`pageInfo`), keyset cursors, not interchangeable with v7's                 |
| `moviesConnection { aggregate { count { nodes } node { year { min max average sum } } } }` | `movieAggregate(where) { _count { _all } _min { year } _max { year } _avg { year } _sum { year } }`             |
| `aggregate { node { title { longest shortest } } }`                                        | no equivalent (`_min` / `_max` compare values, not lengths)                                                     |
| interface root query `learningActivities`                                                  | `learningActivityFindMany` (a Cyphra interface: a shared label, `cyphra import graphql --add-interface-labels`) |
| union root query `contents(where: { Movie: … }, limit, offset)`                            | `contentFindMany(where: { _on: { Movie: … } }, take, skip)`                                                     |
| `@fulltext` query `moviesByTitle(phrase, where: { node, score: { min } }, first)`          | `movieSearch(index, query, mode: lucene, where, minScore, take) { … _score }`                                   |
| full-text `score: { max }`, `sort` other than `score: DESC`, `after`                       | no equivalent (results are sorted by score, best first)                                                         |
| custom `Query` / `Mutation` fields (`@cypher`, resolvers)                                  | [`extend`](#custom-root-fields-and-types) with the same name (kept as is once the native API has it)            |
| `actors(where, sort, limit, offset)`                                                       | `actors(where, orderBy, take, skip)`                                                                            |
| `actorsConnection(where: { node }, sort: [{ node }], first) { edges { properties node } }` | `actors(where, orderBy, take) { … _edge { … } }`                                                                |
| `actorsConnection { totalCount }`, `aggregate { count { nodes } }`                         | `_count { actors(where) }` on the parent                                                                        |
| connection `where: { edge }`, `sort: [{ edge }]`, `after`; nested `pageInfo` / `cursor`    | no equivalent                                                                                                   |
| nested `aggregate { count { edges } node { … } edge { … } }`                               | no equivalent (aggregate the related model with its `Aggregate` root field)                                     |
| `@cypher` field (scalar or nodes)                                                          | [`cypherFields`](#cypher-backed-fields) of the same name                                                        |
| `@customResolver` field                                                                    | a field added with [`extend`](#custom-root-fields-and-types) and its resolver                                   |
| `... on Movie`, fragments, `__typename`                                                    | the same                                                                                                        |
| subscriptions (`movieCreated`, `movieUpdated`, `movieDeleted`)                             | [`movieChanged(operations: [CREATED])`](#subscriptions), … (experimental)                                       |

### Filters and sorting

| v7 (`compat.v7`)                                                                                     | Native                                                                         |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `{ title: { eq: "x" } }`, `title_EQ` (deprecated)                                                    | `{ title: { equals: "x" } }`                                                   |
| `{ in }`, `{ lt }`, `{ lte }`, `{ gt }`, `{ gte }`, `{ contains }`, `{ startsWith }`, `{ endsWith }` | same names                                                                     |
| `{ title: { eq: null } }`                                                                            | `{ title: null }`                                                              |
| list `{ genres: { includes: "x" } }`, `{ genres: { eq: [...] } }`                                    | `{ genres: { has: "x" } }`, `{ genres: { equals: [...] } }`                    |
| `{ matches }` (regular expression)                                                                   | no equivalent                                                                  |
| `AND`, `OR`, `NOT`                                                                                   | the same                                                                       |
| `actors: { some: … }`, `none`                                                                        | the same                                                                       |
| `actors: { all: … }` (needs at least one related node)                                               | `actors: { every: …, some: {} }`                                               |
| `actors: { single: … }`                                                                              | `_count: { actors: { equals: 1, where: … } }`                                  |
| `actors: { some: {} }` (v7 ignores an empty filter)                                                  | dropped                                                                        |
| to-one `author: { … }`, `author: null`                                                               | `author: { is: … }`, `author: null`                                            |
| `actorsConnection: { some: { node: … } }`                                                            | `actors: { some: … }`                                                          |
| `actorsConnection: { some: { edge: … } }`                                                            | no equivalent (no filters on edge properties)                                  |
| `actorsAggregate: { count: { gt: 2 } }`, `aggregate: { count: { nodes: … } }`                        | `_count: { actors: { gt: 2 } }`                                                |
| aggregation filters on `count.edges`, `node` or `edge` fields                                        | no equivalent                                                                  |
| union relationship `favorites: { some: { Movie: … } }`                                               | `favorites: { some: { _on: { Movie: … } } }`                                   |
| union relationship `all` / `single` (per member)                                                     | no equivalent                                                                  |
| interface `typename: [Lab]`                                                                          | `_typename: { in: [Lab] }`                                                     |
| `sort: [{ title: ASC, year: DESC }]`                                                                 | `orderBy: [{ title: asc }, { year: desc }]`                                    |
| a variable holding a v7 input (`$where: MovieWhere`, `$sort`)                                        | no equivalent: write the value inline, or build the native value in the client |

### Mutations

| v7 (`compat.v7`)                                                                  | Native                                                                                         |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `createMovies(input: [{ … }])` (one input)                                        | `movieCreate(data) { … }`                                                                      |
| `createMovies(input: [{ … }, { … }])` without nested writes                       | `movieCreateMany(data) { count nodes { … } }`                                                  |
| several inputs with nested writes                                                 | no equivalent in one field: one `movieCreate` per input                                        |
| `info { nodesCreated }`                                                           | `count` of `movieCreateMany`; the other `info` fields have no equivalent                       |
| nested `create: [{ node, edge }]`                                                 | `create: [{ …node, _edge: edge }]`                                                             |
| nested `connect: [{ where: { node: { id: { eq: "x" } } }, edge }]`                | `connect: [{ id: "x", _edge: edge }]` (a `MERGE`: v7 creates another edge when already linked) |
| `connect` by a non-unique `where`, without `where`, or nested in a `connect`      | no equivalent: connect by unique key, or a custom mutation                                     |
| `updateMovies(where, update: { title: { set: "x" } })`                            | `movieUpdateMany(where, data: { title: "x" }) { nodes }`                                       |

| to-one `disconnect: { }`, `delete: { }`                                           | `disconnect: true`, `delete: true`                                                             |
| nested update of edge properties                                                  | no equivalent (`connect` with `_edge`)                                                         |
| `deleteMovies(where) { nodesDeleted }`                                            | `movieDeleteMany(where) { count }`                                                             |
| `deleteMovies(delete: { … })` (nested delete)                                     | `onDelete: Cascade` in `schema.cyphra`, or a nested `delete` in `movieUpdate`                  |
| nested writes to a union or interface relationship                                | by hand: `connect: { Movie: { … } }`                                                           |
