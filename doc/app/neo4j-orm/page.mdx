# Neo4j ORM? Cyphra is an OGM

If you searched for a **Neo4j ORM**, what you want is an **OGM** (object-graph mapper): the same
job an ORM does for SQL, done for a graph. **Cyphra** is an open-source TypeScript OGM for Neo4j,
Memgraph and FalkorDB, MIT licensed: one schema file, a generated and fully typed client, and
migrations generated from schema changes. Its client follows Prisma's naming (`findMany`,
`include`, `select`, nested writes, `$transaction`), and **Prisma itself does not support Neo4j**.

This page explains what changes when the database is a graph, with code from the Cyphra docs, then
shows the whole workflow and maps the Prisma commands and calls you already know to Cyphra.

## ORM or OGM?

An **ORM** (object-relational mapper) maps **tables, rows and foreign keys** to objects. A relation
between two records is a column holding the other record's key, or a row in a join table, and
loading related records means a `JOIN` (or a second query). Everything compiles to SQL.

An **OGM** maps **nodes, labels and relationships**. A node can carry several labels, so it can
belong to several kinds at once. A relationship is a record of its own: it has a type, a direction
and properties, and the database stores it as a direct link from one node to the other. Queries
follow those links as patterns, any number of hops deep, and compile to a graph query language,
Cypher for Neo4j.

The jobs are the same (describe the model once, get typed objects back, write related records
without assembling queries by hand), so the API can look the same. The model underneath is not,
and a mapper built for tables has no place for edge properties, labels or paths.

### Concepts, side by side

| Relational ORM                   | OGM, and how Cyphra writes it                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------ |
| table                            | label: `node User { … }` matches the nodes labelled `:User`                          |
| row                              | node                                                                                 |
| column                           | property (a scalar field)                                                            |
| primary key, unique column       | `@id`, `@unique`: uniqueness constraints on the label                                |
| foreign key                      | relationship: `@out(AUTHORED)`                                                       |
| join table (many-to-many)        | relationship; its extra columns become a `relationship { … }` model, read as `$edge` |
| `JOIN`                           | a pattern, `(u:User)-[:AUTHORED]->(p:Post)`; `include` / `select` in the client      |
| recursive CTE (`WITH RECURSIVE`) | variable-length path: `traverse`, `shortestPath`, `allShortestPaths`                 |
| table inheritance                | several labels on one node: `interface Person`, `node Employee implements Person`    |
| polymorphic association          | `union SearchHit = Post \| User \| Comment`                                          |
| `ALTER TABLE` migration          | constraints, indexes and data fixes, generated by `cyphra migrate dev`               |
| SQL                              | Cypher                                                                               |

### Relationships with properties

In a graph, data about a link lives on the link: when Alice started following Bob is a property of
the `FOLLOWS` relationship, not of either user. A `relationship { … }` model types it, and the
client reads and writes it as `$edge`:

```cyphra filename="schema.cyphra"
node User {
  id        String @id @default(cuid())
  email     String @unique
  following User[] @out(FOLLOWS)
}

relationship Follows {
  type "FOLLOWS"
  from User
  to User
  since DateTime @default(now())
}
```

```ts
await db.user.update({
  where: { email: "alice@acme.io" },
  data: { following: { connect: { email: "bob@acme.io", $edge: { since: new Date() } } } },
});

const alice = await db.user.findUnique({
  where: { email: "alice@acme.io" },
  include: { following: true },
});
alice?.following[0]?.$edge.since; // Date
```

`connect` `MERGE`s the relationship, so connecting a pair twice keeps one edge. Edge properties can
also be filtered during a traversal (`edgeWhere`, below) and constrained with `@unique` on the
relationship model (Neo4j 5.7+).

### No join tables

The same follow graph in a relational ORM needs a join table, two foreign keys and a composite key.
In Prisma, with the follow date stored on the join row:

```prisma filename="schema.prisma"
model User {
  id        String    @id @default(cuid())
  following Follows[] @relation("follower")
  followers Follows[] @relation("following")
}

model Follows {
  followerId  String
  followingId String
  since       DateTime @default(now())
  follower    User     @relation("follower", fields: [followerId], references: [id])
  following   User     @relation("following", fields: [followingId], references: [id])

  @@id([followerId, followingId])
}
```

In Cyphra the join row is the relationship itself: there is no `followerId` to keep in sync, and
`user.following` returns users, not join records. `cyphra import prisma` does this conversion for
you: foreign keys and join tables become relationships ([details](/cli#import-from-prisma)).

### Multi-label nodes and interfaces

A node can have several labels. An `interface` is a label with shared fields; a node that
implements it carries both labels, and Cyphra writes an `Employee` as `(:Employee:Person)`:

```cyphra
interface Person {
  id    String @id @default(cuid())
  email String @unique
  name  String
}

node Employee implements Person {
  salary Int @default(0)
}

node Customer implements Person {
  tier String @default("free")
}
```

`db.person` queries every implementation, discriminated by `__typename`, and `@unique` on
`Person.email` is one constraint on `:Person`, so an email is unique across employees and
customers:

```ts
const people = await db.person.findMany({ where: { name: { startsWith: "A" } } });
for (const p of people) {
  if (p.__typename === "Employee")
    console.log(p.salary); // number
  else console.log(p.tier); // "Customer": string
}
```

A relational ORM models this with single-table or joined-table inheritance; on a graph it is just
another label. See [Interfaces and multiple labels](/schema#interfaces-and-multiple-labels).

### Unions

Models that share no field (the hits of a search box, the target of a polymorphic relation) are a
`union`. It adds no label: it is matched by a label predicate over its members, so changing it
needs no migration.

```cyphra
union SearchHit = Post | User | Comment

node Board {
  id    String      @id @default(cuid())
  items SearchHit[] @out(SHOWS)
}
```

```ts
const hits = await db.searchHit.findMany({
  where: { $on: { Post: { title: { contains: "graph" } }, User: { name: { startsWith: "Gra" } } } },
  take: 20,
});
// each hit has __typename "Post", "User" or "Comment", and that model's fields
```

In SQL this is a polymorphic association: a `type` column next to an id that no foreign key can
check. Here `Board.items` is a typed relation like any other. See [Unions](/schema#unions) and
[Querying unions](/client#querying-unions).

### Traversals and shortest paths

"Friends of friends" or "how is Alice connected to Dave?" is a recursive CTE in SQL, and most ORMs
leave it to raw SQL. In a graph it is a variable-length path, and Cyphra types it:

```ts
// Everyone Alice follows, and everyone they follow.
const fof = await db.user.traverse({
  from: { email: "alice@acme.io" },
  via: "following",
  depth: { max: 2 },
  take: 20,
});

// The fewest hops from Alice to Dave, with the FOLLOWS edges on the way.
const path = await db.user.shortestPath({
  from: { email: "alice@acme.io" },
  to: { email: "dave@acme.io" },
  via: "following",
  maxDepth: 4,
});
path?.edges[0]; // { type: "FOLLOWS", direction: "out", properties: { since: Date } }
```

`traverse` compiles to one statement with a quantified path pattern (Neo4j 5.9+), `shortestPath`
to a `SHORTEST 1` selector (Neo4j 5.21+). `depth.max` and `maxDepth` are required and capped by the
client option `maxTraversalDepth`. Hops can cross models, and paths can be returned with typed
edges: see [Traversals](/client#traversals) and [Shortest path](/client#shortest-path).

### Constraints instead of table migrations

Neo4j has no table schema: any node can have any property. What it does have are
[constraints](/glossary/constraint) and [indexes](/glossary/neo4j-index), and existing data that
must be fixed when the model changes. So a Cyphra migration does not `ALTER TABLE`: `@id`,
`@unique` and `@index` become `CREATE CONSTRAINT` and `CREATE INDEX` steps, a new field with a
`@default` is backfilled on existing nodes, and a new required field without a default adds a
guard that stops the migration while any node lacks it. The
[migration step below](#4-generate-migrations-from-schema-changes) shows one.

### Cypher, not SQL, and no N+1

An ORM that loads relations lazily runs one query for the users, then one per user for their
posts: the N+1 problem. Cyphra compiles every read, nested `select` and `include` included, to
**one Cypher statement**: each relation becomes a `COLLECT { … }` subquery inside a map projection,
with every value sent as a parameter. This read:

```ts
const user = await db.user.findUnique({
  where: { id },
  select: { name: true, following: true },
});
```

is, simplified, this statement:

```cypher
MATCH (n:`User`) WHERE n.`id` = $p0
RETURN n{.`name`, `following`: COLLECT {
  MATCH (n)-[r1:`FOLLOWS`]->(m0:`User`)
  RETURN m0{.`id`, .`email`, .`name`, `$edge`: properties(r1)}
}} AS row
```

One round trip, however deep the `select`, and the edge properties come back in the same row. That
is why the typed client needs Neo4j 5.6 or later. Nested writes work the same way: a `create` with
nested `create` and `connect` is one operation. When you need Cypher the client does not generate,
`` db.$cypher`…` `` runs a parameterized tagged template. The
[typed queries post](/blog/typed-neo4j-queries-in-typescript) explains how the result types are
built.

### Why people search for "Neo4j ORM"

Because ORM is the word most developers know for "a typed layer between my code and the database",
and Prisma, TypeORM or Drizzle are what they used before. In the Neo4j world the established term
is OGM (Neo4j-OGM for Java, neogma and neode for Node.js), but the search is the same. Whatever it
is called, check that a Neo4j mapper gives you:

- **Result types that follow the query**: `select` and `include` change the type, and typos in
  field names are compile errors.
- **Relationships as first-class data**: typed edge properties, direction, and `connect` that does
  not duplicate edges.
- **Graph queries without raw strings**: traversals, shortest paths, label-based polymorphism.
- **One statement per operation**, so nested reads do not turn into N+1 round trips.
- **Constraints, indexes and data changes as versioned migrations**, since the database will not
  enforce a schema on its own.
- **Raw Cypher one call away**, parameterized, for what the API does not cover.
- **The databases you run**: Cyphra runs on Neo4j 5, [Memgraph](/memgraph) and
  [FalkorDB](/falkordb), with the same schema and client.

The [comparisons](/compare) check neogma, neode, the Neo4j GraphQL Library and the raw driver
against the same points.

## Prisma and Neo4j

Prisma ORM targets relational databases and MongoDB. Its
[supported databases page](https://www.prisma.io/docs/orm/supported-databases), written
for Prisma ORM 8, lists PostgreSQL, MongoDB, MySQL, MariaDB and SQLite, with SQL Server and
CockroachDB marked "coming soon". Neo4j is not on it, and neither is any other graph database.

The feature request for Neo4j support,
[prisma/orm#1575](https://github.com/prisma/orm/issues/1575), was opened in January 2018 and closed
as not planned in December 2024, with a maintainer writing that "supporting Neo4j is currently out
of our foreseeable plans."

The reasons are structural. Prisma's schema and query engine are built around tables (or documents)
and foreign keys, and a graph has things a table does not ([above](#orm-or-ogm)). A Neo4j mapper
has to model them directly, which is why Cyphra has its own schema language instead of reusing
`schema.prisma`.

## Schema, generate, query, migrate

The whole flow, with code from the
[blog example](https://github.com/Cyphra-dev/cyphra/tree/main/examples/blog) in the repository.

### 1. Describe the graph in `schema.cyphra`

Nodes, the relationships between them, and decorators that become Neo4j constraints and indexes.
A `relationship { … }` model types the properties stored on an edge. This is the schema of the
blog example in the repository:

```cyphra filename="schema.cyphra"
node User {
  id        String   @id @default(cuid())
  email     String   @unique
  name      String?
  createdAt DateTime @default(now())
  posts     Post[]   @out(AUTHORED)
  following User[]   @out(FOLLOWS)
}

node Post {
  id        String   @id @default(uuid())
  title     String
  tags      String[]
  published Boolean  @default(false)
  author    User?    @in(AUTHORED)
}

relationship Follows {
  type "FOLLOWS"
  from User
  to User
  since DateTime @default(now())
}
```

The full syntax is on the [Schema](/schema) page.

### 2. Generate the client

```bash
npm i cyphra
npm i -D @cyphra/cli
npx cyphra generate   # writes cyphra.gen.ts
```

`cyphra generate` writes one TypeScript file. Each node model becomes a delegate: `node User` is
`db.user`, `node Post` is `db.post`.

```ts
import { createClient } from "./cyphra.gen.js";

const db = createClient({
  uri: process.env.NEO4J_URI!,
  user: process.env.NEO4J_USERNAME!,
  password: process.env.NEO4J_PASSWORD!,
});
```

### 3. Query with types inferred from the schema

```ts
// One write transaction: a user, two posts, and a FOLLOWS edge with a typed `since`.
const alice = await db.user.create({
  data: {
    email: "alice@acme.io",
    name: "Alice",
    posts: { create: [{ title: "Hello graph", published: true }, { title: "Draft" }] },
    following: { connect: { email: "bob@acme.io" } },
  },
  include: { posts: true, following: true },
});
alice.posts[0]?.title; // string
alice.following[0]?.$edge.since; // Date, from the Follows relationship model

const authors = await db.user.findMany({
  where: { posts: { some: { published: true } } },
  select: { name: true, posts: { where: { published: true }, select: { title: true } } },
  orderBy: { email: "asc" },
});
// { name: string | null; posts: { title: string }[] }[]

await db.$transaction(async (tx) => {
  const post = await tx.post.create({ data: { title: "Graphs in TypeScript" } });
  await tx.post.update({
    where: { id: post.id },
    data: { author: { connect: { email: "alice@acme.io" } } },
  });
});
```

Typos are compile errors, and the result type follows `select` and `include`:

```text
error TS2561: Object literal may only specify known properties, but 'emial' does not exist
in type 'WhereInput<CyphraTypeMap, "User">'. Did you mean to write 'email'?

error TS2339: Property 'email' does not exist on type '{ name: string | null; }'.
```

Filters, nested writes, value mapping and errors are documented on the [Typed client](/client)
page. The [typed queries post](/blog/typed-neo4j-queries-in-typescript) explains how the types are
built.

### 4. Generate migrations from schema changes

Neo4j has no table schema, but it has [constraints](/glossary/constraint) and
[indexes](/glossary/neo4j-index) that must follow your model, and existing data that must be fixed
when the model changes. `cyphra migrate dev` diffs your schema against the last snapshot and writes
a reviewable migration. For the schema above, the first one is:

```js filename="migrations/20261120143911_init.mjs"
// Generated by `cyphra migrate dev`. Review it before applying to shared databases.
import { defineMigration } from "cyphra";

export default defineMigration({
  name: "20261120143911_init",
  async up({ db }) {
    // Create constraint User_id_id.
    await db.execute(
      "CREATE CONSTRAINT User_id_id IF NOT EXISTS FOR (n:`User`) REQUIRE n.`id` IS UNIQUE",
    );

    // Create constraint User_email_unique.
    await db.execute(
      "CREATE CONSTRAINT User_email_unique IF NOT EXISTS FOR (n:`User`) REQUIRE n.`email` IS UNIQUE",
    );

    // Create constraint Post_id_id.
    await db.execute(
      "CREATE CONSTRAINT Post_id_id IF NOT EXISTS FOR (n:`Post`) REQUIRE n.`id` IS UNIQUE",
    );
  },
});
```

Later changes also generate data steps: a new field with a `@default` is backfilled on existing
nodes, and a new required field without a default adds a guard that stops the migration if any
node lacks it. Removed fields and models are written commented out, so deleting data is something
you opt into. See [Migrations](/migrations) and the post on
[constraints and indexes as code](/blog/neo4j-schema-migrations-constraints-as-code).

```bash
npx cyphra migrate dev --name init   # generate from schema changes, then apply
npx cyphra migrate status            # pending, applied, modified; non-zero exit for CI
npx cyphra migrate deploy            # production: apply pending migrations only
```

<Callout type="info">
  Need a database? `npx cyphra dev` starts a local Neo4j 5 in Docker, bound to 127.0.0.1, and writes
  `.env`. The [Getting started](/getting-started) guide walks through all of it from an empty
  folder.
</Callout>

## Coming from Prisma

Moving an existing Prisma app? `cyphra import prisma prisma/schema.prisma` converts the schema:
models become nodes, foreign keys and join tables become relationships, and a report lists what
does not convert. The [migration guide](/guides/migrate-from-prisma) goes on with the data and the
queries.

The left column uses the names from the Prisma ORM 7
[CLI](https://www.prisma.io/docs/orm/v7/reference/prisma-cli-reference) and
[client](https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference) references.

| Prisma                                         | Cyphra                                                                                                    |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `schema.prisma`                                | `schema.cyphra` (`cyphra import prisma` converts one: [details](/cli#import-from-prisma))                 |
| `model User { … }`                             | `node User { … }`                                                                                         |
| `@relation(fields: […], references: […])`      | `@out(AUTHORED)` / `@in(AUTHORED)`                                                                        |
| implicit or explicit many-to-many join table   | a relationship; its properties go in a `relationship { … }` model                                         |
| `@id`, `@unique`, `@@index`                    | `@id`, `@unique`, `@index` (Neo4j constraints and range indexes)                                          |
| `prisma generate`                              | `cyphra generate`                                                                                         |
| `prisma migrate dev` / `deploy` / `status`     | `cyphra migrate dev` / `deploy` / `status`                                                                |
| `prisma migrate diff`                          | `cyphra migrate diff`                                                                                     |
| `prisma db pull`                               | `cyphra pull`                                                                                             |
| `prisma db push`                               | `cyphra push` (constraints and indexes only)                                                              |
| `prisma.user.findMany({ where, include })`     | `db.user.findMany({ where, include })`                                                                    |
| `select`, `orderBy`, `skip`, `take`            | same names, also inside a nested relation                                                                 |
| `create` with nested `create` / `connect`      | same, plus `$edge` to set relationship properties                                                         |
| `upsert`                                       | same; one atomic `MERGE` on the `@id` / `@unique` key                                                     |
| `lt`, `gt`, `contains`, `in`, … filters        | same names; `lt` / `gt` also on strings                                                                   |
| `aggregate`, `groupBy` with `having`           | same shapes ([Aggregations](/client#aggregations))                                                        |
| `_count` in `select` / `include`, `orderBy`    | same shapes ([Counting](/client#counting-related-nodes))                                                  |
| no equivalent (no multi-hop queries)           | `db.user.traverse({ from, via, depth })` ([Traversals](/client#traversals))                               |
| no equivalent (no path queries)                | `db.user.shortestPath({ from, to, via, maxDepth })` ([Shortest path](/client#shortest-path))              |
| no equivalent (no vector search)               | `db.chunk.findSimilar({ field, vector, k, where })` ([Vector search](/client#vector-search))              |
| `@@fulltext` and the full-text `search` filter | `@@fulltext` and `db.post.search({ index, query, where })` ([Full-text search](/client#full-text-search)) |
| `$transaction(async (tx) => …)`                | `db.$transaction(async (tx) => …)`                                                                        |
| `$queryRaw` tagged template                    | `` db.$cypher`…` `` (parameterized Cypher)                                                                |
| `$extends({ query, result, model, client })`   | `db.$extends({ query, result, model, client })` ([Extensions](/client#extensions))                        |
| `$disconnect()`                                | `db.$disconnect()`                                                                                        |

Some things do not map, and it is better to know before you start:

- **No array form of `$transaction`.** Cyphra has the interactive form only.
- **Cursors are opaque strings**, not a unique `where`: select `$cursor` and pass it as
  `cursor: { after }` (keyset pagination, see [Cursor pagination](/client#cursor-pagination)).
- **No down migrations.** Migrations are forward-only.
- **Relations are relationships, not foreign keys.** There is no `userId` field to keep in sync:
  `connect` and `disconnect` create and delete edges (`connect` is idempotent: one edge per pair).

## When Cyphra is not the right tool

- Your data is relational and you have no reason to move it into a graph: use a relational ORM
  such as Prisma on PostgreSQL or MySQL.
- You want a GraphQL API generated from your graph model with subscriptions, Apollo Federation or
  interfaces: use the [Neo4j GraphQL Library](/compare/neo4j-graphql-library). For the rest of its
  v7 API, [`@cyphra/graphql`](/graphql) serves the same API from the same type definitions.
- Most of your queries are hand-tuned Cypher and you do not want generated code: use the
  [official driver directly](/compare/neo4j-driver).

The [comparisons](/compare) cover these trade-offs in more detail, and the
[benchmarks](/benchmarks) measure what the client layer costs against the raw driver.

## FAQ

### Is Cyphra an ORM?

Strictly, no: Cyphra is an OGM (object-graph mapper). It maps nodes, labels and relationships rather than tables and rows, and it generates Cypher rather than SQL. Its client follows the ORM conventions TypeScript developers know (findMany, include, select, nested writes), so it fills the role people mean when they search for a Neo4j ORM.

### What is the difference between an ORM and an OGM?

An ORM maps relational tables, rows and foreign keys to objects and generates SQL. An OGM maps graph nodes, labels and relationships to objects and generates a graph query language such as Cypher. In a graph, relationships are records of their own, with a type, a direction and properties, so an OGM models them directly instead of through foreign keys and join tables.

### Can I use Cyphra like Prisma?

Yes, for the workflow: a schema file, cyphra generate for the typed client, and cyphra migrate dev, status and deploy for migrations. The client uses the same names as Prisma Client (findMany, include, select, orderBy, upsert, $transaction). It adds graph features Prisma has no equivalent for, such as typed edge properties, traverse and shortestPath, and cyphra import prisma converts an existing schema.prisma.

### Does Cyphra work with Memgraph or FalkorDB?

Yes. Set the memgraph dialect for Memgraph 3.x over Bolt, or pass the falkordb option for FalkorDB over the Redis protocol. CI runs the client, migration and CLI suites against both. A feature a database has no equivalent for throws an UnsupportedFeatureError before anything runs: interactive transactions, for example, are not available on FalkorDB.

### Does Prisma support Neo4j?

No. Prisma ORM supports relational databases and MongoDB, and Neo4j is not on its list of supported databases. The GitHub feature request for Neo4j support was closed as not planned in December 2024.

### Is Cyphra a fork of Prisma?

No. Cyphra is a separate open-source project under the MIT license. Its client follows Prisma's naming (findMany, include, select, $transaction) so the patterns carry over, but the schema language, the code generator and the migration engine are written for Neo4j.

### Which Neo4j versions does Cyphra need?

The typed client needs Neo4j 5.6 or later, because it compiles relations to COLLECT and EXISTS subqueries. Relationship property uniqueness constraints need Neo4j 5.7 or later, traversals (traverse) need Neo4j 5.9 or later, vector indexes and findSimilar need Neo4j 5.15 or later (full-text indexes and search work on any Neo4j 5), and shortest paths (shortestPath, allShortestPaths) need Neo4j 5.21 or later.

### Can I use Cyphra with an existing Neo4j database?

Yes. cyphra pull reads labels, relationship types, property types, constraints and indexes from a live database and writes a .cyphra schema for you to review. cyphra generate then builds the typed client from it.

### Can I still write Cypher?

Yes. db.$cypher runs a parameterized tagged template and returns plain JavaScript values, and the query builder and the runtime under the client are exported from the same cyphra package.

### Does Cyphra have down migrations?

No. A Cyphra migration is a module with a single up function, and applied migrations are tracked in the database. To undo a change, generate or write a new migration.
