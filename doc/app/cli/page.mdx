# CLI

The `cyphra` command starts a local database, validates your schema, generates the typed client and
runs migrations. Install it as a dev dependency:

```bash
pnpm add -D @cyphra/cli
```

App code depends on **`cyphra`** separately (see [Getting started](/getting-started#install)). The CLI loads `./.env` automatically.

| Command                          | Description                                                                                                                                                         |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cyphra init`                    | Scaffold `cyphra.json`, `schema.cyphra`, `migrations/`, `.env.example` (existing files are kept)                                                                    |
| `cyphra dev`                     | Run a local Neo4j 5 in Docker for this project and write `.env` (`--stop`, `--reset`, `--port`, `--http-port`, `--image`, `--watch`)                                |
| `cyphra generate`                | Generate the [typed client](/client) (`cyphra.gen.ts`) and, if configured, [zod schemas](#zod-schemas) (`--watch`, `--zod`, `--zod-coerce`, `--zod-omit-generated`) |
| `cyphra migrate dev`             | Generate a migration from schema changes, then apply pending ones (`--name`, `--create-only`)                                                                       |
| `cyphra migrate diff`            | Print the migration `migrate dev` would generate                                                                                                                    |
| `cyphra migrate deploy`          | Apply pending migrations                                                                                                                                            |
| `cyphra migrate status`          | Applied / pending / modified migrations, uncaptured changes and [drift](/migrations#drift-detection) (`--json`, `--schema`; exit 1)                                 |
| `cyphra migrate reset`           | Empty a local database, reapply every migration, then run the seed (`--yes`, `--force`, `--skip-seed`)                                                              |
| `cyphra db seed`                 | Run the `seed` command from `cyphra.json`                                                                                                                           |
| `cyphra studio`                  | Browse and edit the data in a local web UI built from the schema ([details](#cyphra-studio); `--port`, `--host`, `--no-open`, `--read-only`)                        |
| `cyphra migration:create <name>` | Empty `.mjs` migration to write by hand                                                                                                                             |
| `cyphra pull`                    | Introspect the database and write `schema.cyphra` (`--print`, `--force`, `--interface <labels…>`)                                                                   |
| `cyphra import graphql <files>`  | Convert `@neo4j/graphql` v7 type definitions to `schema.cyphra` (`--out`, `--merge`, `--force`, `--print`)                                                          |
| `cyphra import prisma <schema>`  | Convert a Prisma schema to `schema.cyphra`, foreign keys to edges ([details](#import-from-prisma); `--out`, `--merge`, `--force`, `--print`)                        |
| `cyphra import neogma <files>`   | Convert neogma models (decorator classes or `ModelFactory`) to `schema.cyphra` ([details](#import-from-neogma); `--out`, `--merge`, `--force`, `--print`)           |
| `cyphra push`                    | Apply constraints and range, vector and full-text indexes directly (prototyping)                                                                                    |
| `cyphra validate`                | Parse and validate the schema                                                                                                                                       |
| `cyphra format`                  | Format the schema in place, keeping comments (`--check` exits with 1 instead of writing)                                                                            |
| `cyphra schema print`            | Canonical pretty-print of the schema                                                                                                                                |
| `cyphra schema ddl`              | Print the constraint and index DDL (no database)                                                                                                                    |

## cyphra.json

```json
{
  "schema": "./schema.cyphra",
  "migrations": "./migrations",
  "generate": "./cyphra.gen.ts",
  "runtimeImport": "cyphra",
  "dialect": "neo4j",
  "seed": "tsx seed.ts",
  "generators": {
    "zod": { "output": "./src/cyphra.zod.ts", "coerce": true }
  }
}
```

`runtimeImport` is the module that generated files (the client and migrations) import from. Set it to
`@cyphra/runtime` if you depend on the scoped packages instead of `cyphra`. `seed` is optional: see
[cyphra db seed](#cyphra-db-seed). `generators` is optional: see [zod schemas](#zod-schemas).
`dialect` is `"neo4j"` (default), `"memgraph"` or `"falkordb"`: it decides the DDL that
`migrate dev`, `migrate diff` and `schema ddl` write. Commands that connect use it too; when it is
not set, they detect Memgraph from the server (see [Memgraph](/memgraph)). With `"falkordb"`, they
connect to `FALKORDB_URL` (default `redis://localhost:6379`) and the graph `FALKORDB_GRAPH`
instead of the `NEO4J_*` variables (see [FalkorDB](/falkordb)).

## Zod schemas

With `generators.zod` in `cyphra.json`, `cyphra generate` (and `--watch`, and `cyphra dev --watch`)
also writes a module of [zod](https://zod.dev) schemas, to validate API input against the schema
before it reaches the client. Install zod in your project (`pnpm add zod`); the generated code works
with zod 4 and zod 3.

| Option          | Default             | Description                                                                                                                               |
| --------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `output`        | `"./cyphra.zod.ts"` | File to write, under the project root                                                                                                     |
| `coerce`        | `false`             | Read ISO 8601 strings as `Date`s (`DateTime`, `Date`) and decimal strings or safe integers as `bigint`s (`BigInt`)                        |
| `import`        | `"zod"`             | Module to import `z` from (`"zod/v4"` to use zod 4 from zod 3.25)                                                                         |
| `omitGenerated` | `false`             | Leave generated fields out of the create and update input schemas: an `@id` with a `@default`, and `now()` / `cuid()` / `uuid()` defaults |

`"zod": true` takes every default. Without the config, `cyphra generate --zod [output]` writes the
schemas for that run (`--zod-coerce` adds coercion, `--zod-omit-generated` sets `omitGenerated`);
the flags also override `cyphra.json`.

```bash
cyphra generate --zod                       # cyphra.gen.ts and cyphra.zod.ts
cyphra generate --zod src/db/zod.ts --zod-coerce
cyphra generate --zod --zod-omit-generated  # no id / createdAt in the input schemas
```

With `omitGenerated`, a public API takes `UserCreateInputSchema` as is, instead of
`UserCreateInputSchema.omit({ id: true, createdAt: true })`: the client fills those fields on
create, and callers cannot send them. Literal defaults (`@default("member")`) stay in the inputs,
optional. The output schema (`UserSchema`) keeps every field. For a model that needs a generated
field back, `.extend()` its input with `UserSchema.shape.<field>`.

For each node model `User` the module exports `UserSchema` (the properties the client returns),
`UserCreateInputSchema` and `UserUpdateInputSchema`; the same three for each relationship model
(its edge properties), and `RoleSchema` (`z.enum([...])`) for each enum. See
[Validating API input with zod](/client#validating-api-input-with-zod) for what they check.

## Environment

Commands that talk to Neo4j (`migrate dev | deploy | status | reset`, `pull`, `push`) read
`NEO4J_URI`, `NEO4J_USERNAME` (`NEO4J_USER` also works), `NEO4J_PASSWORD` and optionally
`NEO4J_DATABASE`. The seed command inherits the same environment.

## cyphra migrate status

Shows where the database stands against your migrations:

```bash
cyphra migrate status            # human report
cyphra migrate status --json     # one JSON document on stdout
cyphra migrate status --schema   # compare with schema.cyphra instead of the applied migrations
```

It lists each migration as `applied`, `pending`, `modified` (the file changed after it was applied:
checksum mismatch) or `missing` (applied, but the file is gone), counts schema changes that no
migration captures yet, and reports [drift](/migrations#drift-detection): constraints and indexes
that are extra, missing or defined differently in the database than the applied migrations made
them. It exits with `0` when everything is in sync, `1` when anything needs attention, and `2` when
the check could not run, so it can gate CI (see the
[GitHub Actions example](/migrations#in-ci)). `cyphra migrate dev` runs the drift check before it
generates a migration and warns when the database has drifted.

## cyphra dev

Starts `neo4j:5` in a container named after your project folder, bound to **127.0.0.1 only**, with data
in a named Docker volume. It waits until Neo4j accepts connections and writes `.env` if there is none:

```bash
cyphra dev            # start (or restart) and wait until ready
cyphra dev --stop     # stop, keep data
cyphra dev --reset    # remove the container and its data
cyphra dev --watch    # start, then regenerate the client on schema changes (see below)
```

`cyphra dev --reset` deletes the container. To keep it and only empty the database, use
[`cyphra migrate reset`](/migrations#reset-a-development-database).

## Watch mode

`cyphra generate --watch` (or `-w`) generates the client, then watches the schema file from
`cyphra.json` and regenerates `cyphra.gen.ts` (and the [zod schemas](#zod-schemas), when configured)
each time you save it:

```text
$ cyphra generate --watch
[10:42:01] Wrote cyphra.gen.ts
Watching schema.cyphra for changes (Ctrl+C to stop).
[10:42:17] schema.cyphra: Node "Post" field "author": unknown node "Usr" (not a node model or an enum).
[10:42:25] Wrote cyphra.gen.ts
```

- Saves are debounced (100 ms), so one save triggers one regeneration.
- An invalid schema prints its error and the previous `cyphra.gen.ts` stays in place; the watcher
  keeps running until the next save.
- The schema's directory is watched rather than the file, so editors that save by writing a
  temporary file and renaming it over the original (vim, JetBrains IDEs) are picked up. It uses
  `fs.watch` and works on Linux, macOS and Windows.
- Ctrl+C stops watching and exits with 0.

`cyphra dev --watch` starts Neo4j first, then watches the same way. Ctrl+C stops the watcher; the
container keeps running until `cyphra dev --stop`.

## cyphra db seed

Set `seed` in `cyphra.json` to the command that loads your data. It is a shell command, run from the
project root, so it can use any runtime:

```json
{ "seed": "tsx seed.ts" }
```

```ts filename="seed.ts"
import { createClient } from "./cyphra.gen.js";

const db = createClient({
  uri: process.env.NEO4J_URI!,
  user: process.env.NEO4J_USERNAME!,
  password: process.env.NEO4J_PASSWORD!,
});
await db.user.create({ data: { email: "ada@example.com" } });
await db.$disconnect();
```

`cyphra db seed` runs it with the CLI's environment (including `./.env`) and with
`node_modules/.bin` on `PATH`, so a locally installed `tsx` is found. The seed's exit code becomes the
command's exit code; without a `seed` entry, `cyphra db seed` fails with 1.
[`cyphra migrate reset`](/migrations#reset-a-development-database) runs the seed after reapplying
migrations.

## cyphra studio

A local data browser built from `schema.cyphra`: no Neo4j Browser, no codegen. It reads `cyphra.json`
and the `NEO4J_*` settings (including `./.env`), starts a web server on `127.0.0.1` and opens your
browser:

```text
$ cyphra studio
Cyphra Studio on http://127.0.0.1:5555/?token=Qk3…
The token in the URL is required: keep it private. Stop with Ctrl+C.
```

<img
  src="/cli/cyphra-studio.webp"
  width={1360}
  height={800}
  alt="Cyphra Studio: the User model as a table with typed columns, a karma ≥ 600 filter and a descending sort"
/>

- **Models.** The sidebar lists node models, interfaces and relationship models with their counts.
  Each model opens as a table with the field types in the header, pagination, sorting by column
  (to-many relations sort by their count) and a filter builder whose operators follow the field type
  (`contains` and case-insensitive matches on strings, ranges on numbers and dates, `has` and
  `isEmpty` on lists, `some` / `none` on relations, `is null` everywhere).
- **Editing.** Double-click a cell to edit it, or open the record to edit every field with typed
  inputs: a select for enums and booleans, date and time pickers, a JSON editor that validates as
  you type, item lists for `String[]` and friends, coordinates for points. Writes go through the
  ORM, so [validation rules](/schema#validation-rules) and unique constraints apply and their messages show next to
  the field.
- **Relations.** Relation columns show the related node's key or the count of related nodes; click
  one to open the related records, and keep following from there (a breadcrumb leads back). Edge
  properties of a `relationship { … }` model show next to the related nodes and in the
  relationship model's own table, where they can be edited.
- **Delete.** Before deleting, the studio lists what the [`onDelete` rules](/client#deleting) will do:
  nodes deleted by a cascade, edges removed, or a `Restrict` relation that blocks the delete.
- **Cypher.** A raw Cypher tab with JSON parameters. Queries run in a **read transaction**; tick
  _Allow writes_ to run one in a write transaction.
- **Interfaces.** An interface lists the nodes of every implementation, with their `__typename`;
  edits go to the implementation.

Records of a model without an `@id`, `@unique` or `@@unique` field can be browsed but not edited
(nothing identifies one record).

**Memgraph.** The studio uses the `"dialect"` of `cyphra.json`, or, when it sets none, detects
Memgraph from the server (as `push` and `migrate deploy` do), and shows a _Memgraph_ badge. Fields
Memgraph cannot store (`Time`) are read-only and left out of the filter builder; the API refuses
to write them, and answers anything else Memgraph lacks (a `Duration` with months, a Neo4j-only
procedure in the Cypher tab) with a 400 and the reason, without retrying. See the
[feature matrix](/memgraph#feature-matrix).

| Option        | Description                                                                          |
| ------------- | ------------------------------------------------------------------------------------ |
| `--port <n>`  | Port to listen on (default `5555`)                                                   |
| `--host <h>`  | Address to bind (default `127.0.0.1`); any other address prints a warning            |
| `--no-open`   | Print the URL without opening a browser                                              |
| `--read-only` | No edits, creates, deletes or Cypher writes: the API refuses them, the UI hides them |

### Security

The studio holds your database credentials, so it only answers the page it served:

- **Loopback only by default.** It binds `127.0.0.1`. Exposing it to the network takes an explicit
  `--host`, and prints a warning.
- **Session token.** Each run creates a random token. The URL carries it once: the studio moves it to
  an `HttpOnly`, `SameSite=Strict` cookie and drops it from the address bar. Every API call needs
  that cookie and a custom header, which other sites cannot send without a CORS preflight the studio
  never grants (CSRF).
- **DNS rebinding.** Requests whose `Host` is not an IP address, `localhost` or the `--host` name are
  refused, as are requests from another `Origin`.
- **No credentials in the browser.** The page gets the schema and the database address without user
  name, password or query string. Queries run on the server.
- **Strict page.** The UI is bundled in the CLI (no CDN) and served with a Content-Security-Policy
  that allows only its own scripts and styles, and no framing.

Treat the printed URL like a password, and prefer `--read-only` against shared or production
databases.

## cyphra pull

Reads labels, relationship types, property types, constraints and indexes from a live database and
writes a `.cyphra` schema. It is read-only and samples up to 10,000 edges per relationship type to find
their endpoints. Review the result:

- Relation names are derived from relationship types (`AUTHORED` becomes `authored` on the start node
  and `authoredBy` on the end node), and every relation is to-many.
- A property is required only if every node with that label had it at pull time.
- Single-property uniqueness constraints become `@id` (on a property named `id`) or `@unique`; range
  and point indexes become `@index`. Composite uniqueness constraints (and node keys) become
  `@@unique([…])`, composite range indexes `@@index([…])`, with a `name` when theirs is not the
  default.
- `LocalDateTime`, `LocalTime`, `Time` and `Duration` properties keep their type. A point property
  becomes a `Point` or a `CartesianPoint` from the CRS of up to 10,000 sampled values; a property
  holding both kinds is skipped with a warning.
- Node vector indexes become `Vector(N)` fields with `@vectorIndex(similarity: …)`, keeping the index
  name when it is not the default one (and `quantization: false` when it is off).
- Node full-text indexes become `@@fulltext([…])` attributes, keeping the name, analyzer and
  `eventuallyConsistent: true` when they are not the defaults. Indexes over several labels, on
  relationships, or on properties that were not pulled as `String` / `String[]` fields are skipped
  with a warning.
- Nodes with several labels are read as one model each, plus interfaces and dynamic labels. In
  each group of labels seen together, `pull` picks one label per node as its model, so that every
  label combination holds exactly one model label. Each other label is then:
  - an [`interface`](/schema#interfaces-and-multiple-labels) when it is on every node of the
    models it is seen with (never alone). It gets the properties all its nodes share (and those its
    constraints cover), and each model `implements` it with the rest. A node can implement several
    unrelated interfaces: `[Employee, Person, Archivable]`, `[Customer, Person]` and
    `[Doc, Archivable]` give `node Employee implements Archivable, Person`. Interfaces whose nodes
    all carry another one [extend it](/schema#interfaces-extending-interfaces): with
    `[Employee, Staff, Person]`, `[Contractor, Staff, Person]` and `[Customer, Person]`, `pull`
    writes `interface Staff extends Person`, `node Employee implements Staff`,
    `node Contractor implements Staff` and `node Customer implements Person`. A property two
    unrelated interfaces of a node could both hold stays on the nodes, unless only one of the
    interfaces constrains or indexes it.
  - a [dynamic label](/schema#dynamic-labels) (`@@labels([Archived])`) when it is on some nodes of
    the model only, its nodes have no property the model's other nodes never have, it has no
    constraint or index, and some nodes of the model carry none of the model's dynamic labels.
    With `[Post]`, `[Post, Archived]` and `[User, Archived]`, both `Post` and `User` get
    `@@labels([Archived])`. When every `:Post` is also `:Draft` or `:Published`, those are the
    models and `Post` their interface.

  A layout that fits none of this stays one model per label, with a warning. So does one that
  fits in several ways: nodes always labelled `[Employee, Person]` (a shared label with a single
  implementation) could be either way round. Tell `pull` which labels are interfaces there:
  `cyphra pull --interface Person` (repeat the label, or give a comma-separated list, for several).

- Unsupported or mixed types (e.g. a property that is a string on some nodes and an integer on
  others) and names that are not identifiers are skipped with a warning.
- Integers are pulled as `Int` and strings as `String`: the database cannot tell a `BigInt`, an enum
  or a `Json` field apart from those. Change the types by hand where it applies (for example an
  `Int` whose values exceed 2^53 to `BigInt`, a status string to an [enum](/schema#enums)).

## Import from @neo4j/graphql

If your app runs on `@neo4j/graphql` v7, convert its type definitions to a Cyphra schema in one step:

```bash
cyphra import graphql typeDefs.graphql            # writes the schema from cyphra.json
cyphra import graphql src/**/*.graphql --merge    # add to an existing schema.cyphra
```

Pass one or more `.graphql` files. The schema goes to the `schema` path in `cyphra.json` (or
`./schema.cyphra`), or to `--out <path>`. An existing file is never overwritten unless you pass
`--force`. With `--merge`, your models, fields and comments stay as they are: missing fields and new
models are added, and when a field exists on both sides your version wins.

What converts:

- `@node` types become `node` models. A custom label in `@node(labels)` becomes the model name, since a
  Cyphra model's name is its label.
- `ID`, `String`, `Int`, `Float`, `BigInt`, `Boolean`, `DateTime`, `Date`, `LocalDateTime`,
  `LocalTime`, `Time`, `Duration`, `Point` and `CartesianPoint` (the same Neo4j types), lists, and
  required or optional from nullability. Enums become [Cyphra enums](/schema#enums) with the same
  values (only the ones a converted field uses).
- `@id` becomes `@id @default(uuid())`, `@timestamp` (on `DateTime` and `Time`) becomes
  `@default(now())`, `@default` keeps its value, and `@unique` (from v6 and earlier) stays `@unique`.
- `@relationship(type, direction)` becomes a relation field, and a `@relationshipProperties` type
  becomes a `relationship` model.
- `@fulltext(indexes: [{ indexName, queryName, fields }])` becomes one
  [`@@fulltext([fields], name: indexName)`](/schema#full-text-indexes) per index, so `cyphra migrate`
  creates the indexes. `queryName` names a GraphQL query field and is listed as ignored.

Everything else is listed in a report, never dropped silently. Fields that were not converted also
appear as comments in the schema. The command exits with 0 when it wrote the schema, warnings included,
and with 1 only when the type definitions are not valid GraphQL:

```text
Wrote schema.cyphra (2 node(s), 1 relationship model(s))

Not converted (2):
  Person         @node(labels): extra labels "Actor" are not supported: Cyphra nodes have one label
  Movie.similar  @cypher: @cypher fields are computed by a Cypher query: not converted (compat.v7 still serves it); with the typed client, write it as a query

Converted with differences (3):
  Movie.id     @id: became @id @default(uuid()); Cyphra also adds a uniqueness constraint, which v7 @id does not
  Person.id    @id: became @id @default(uuid()); Cyphra also adds a uniqueness constraint, which v7 @id does not
  Person.name  @unique: @unique was removed in @neo4j/graphql v7; Cyphra keeps it and creates the uniqueness constraint
```

Not converted today: custom scalars, interfaces and unions (`@neo4j/graphql` interfaces are not labels, so they do not map to [Cyphra interfaces](/schema#interfaces-and-multiple-labels); declare one and backfill its label if you want that layout), extra labels, `@cypher` and
`@customResolver` fields, `@authentication` and `@authorization` rules, `@vector` indexes (the type
definitions carry neither the dimensions nor the similarity: declare a
[`Vector(N)` field with `@vectorIndex`](/schema#vector-fields) by hand), and update timestamps. API-only settings such as `@plural`, `@selectable` or `@filterable`
are listed as ignored. Run `cyphra validate` after the import, then `cyphra migrate dev`.

## Import from Prisma

Moving from Prisma and PostgreSQL (or MySQL, SQLite, MongoDB) to Neo4j? Convert `schema.prisma` to a
Cyphra schema, with foreign keys turned into edges:

```bash
cyphra import prisma prisma/schema.prisma         # writes the schema from cyphra.json
cyphra import prisma prisma/schema                # a multi-file schema folder
cyphra import prisma prisma/schema.prisma --print # to stdout, report on stderr
```

The options are the ones of [`cyphra import graphql`](#import-from-neo4jgraphql): `--out <path>`,
`--force` to overwrite, `--merge` to add to an existing schema without touching what is there, and
`--print`. Prisma itself is not needed: the importer reads the file. The
[migration guide](/guides/migrate-from-prisma) covers the rest of the move (data and queries).

**Models, fields and attributes**

| Prisma                                                            | Cyphra                                                                 |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `model`, `enum`                                                   | `node`, `enum` (same names, same values)                               |
| `String`, `Int`, `BigInt`, `Float`, `Boolean`, `DateTime`, `Json` | the same types                                                         |
| `Decimal`                                                         | `Float`, reported: about 15 significant digits                         |
| `?`, `[]` (scalar lists)                                          | `?`, `[]`; `Json[]` becomes one `Json` holding the array               |
| `@id`, `@unique`, `@@unique([a, b])`, `@@index([a, b])`           | the same; one-field `@@unique` / `@@index` become `@unique` / `@index` |
| `@@id([a, b])`                                                    | `@@unique([a, b])`, reported (a Cyphra `@id` is one field)             |
| `@@fulltext([a, b])`                                              | `@@fulltext([a, b])`                                                   |
| `@default(cuid())`, `uuid()`, `now()`, a literal                  | the same                                                               |
| `@default(uuid(7))`, `ulid()`, `nanoid()`, `auto()`               | `uuid()` or `cuid()`, reported                                         |
| `@default(dbgenerated("gen_random_uuid()"))`                      | `@default(uuid())`, reported (other SQL is not converted)              |
| `@updatedAt`                                                      | `@default(now())`, reported: set it yourself on update                 |
| `@db.VarChar(n)`, `@db.Char(n)`                                   | `@length(max: n)`, checked by the client                               |
| `DateTime @db.Date`, `@db.Time`, `@db.Timetz`                     | `Date`, `LocalTime`, `Time`                                            |

**Relations**

- A **foreign key** (`author User @relation(fields: [authorId], references: [id])` with
  `authorId String`) becomes an edge from the referenced model to the model holding the key,
  `(User)-[:HAS_POSTS]->(Post)`: `User.posts` is `OUT`, `Post.author` is `IN`. The key scalar
  (`authorId`) is dropped, since the edge is the link, and left as a comment in the model. One-to-one
  and one-to-many work the same way.
- An **implicit many-to-many** (`tags Tag[]` on `Post`, `posts Post[]` on `Tag`) becomes one edge
  type, from the model whose name sorts first (Prisma's `A` side): `(Post)-[:HAS_TAGS]->(Tag)`.
- An **explicit join model** becomes a [`relationship` model](/schema#relationships) when it has
  exactly two required relations, a `@@id` or `@@unique` over their keys, and nothing else pointing
  to it. Its other fields become edge properties: `OrderItem { order, product, quantity }` becomes
  `relationship OrderItem`, `ORDER_ITEM` edges from `Order` to `Product` with a `quantity`
  property, and `Order.items` lists products, each with its `$edge`. The row's own `id`, if any, is dropped.
- **Edge type names.** `@relation("WrittenPosts")` gives `WRITTEN_POSTS` (upper snake case). A
  join model gives its name (`ORDER_ITEM`). Otherwise, `HAS_` and the field on the edge's start
  model: `User.posts` gives `HAS_POSTS`, `Post.tags` gives `HAS_TAGS`. A name already used between
  the same two models gets a `_2` suffix. Rename them before your first migration if you prefer
  verbs (`AUTHORED`): the type is only in `schema.cyphra`.
- **`onDelete`** moves to the referenced model's field, where a [Cyphra rule](/schema#ondelete-rules)
  lives: `Post.author … onDelete: Cascade` becomes `onDelete: Cascade` on `User.posts`. `Restrict`
  stays `Restrict`, `NoAction` becomes `Restrict`, `SetNull` is Cyphra's default and `SetDefault` is
  reported. Without `onDelete`, Prisma's default applies: `Restrict` for a required key, `SetNull`
  for an optional one. On a join model, `Cascade` needs no rule, since deleting a node removes its
  edges. `onUpdate` has no equivalent (edges hold no key values) and is listed as ignored.
- `@@index` on foreign keys is dropped (Neo4j follows the edge), and a key is removed from a
  composite `@@index`. A `@@unique` that covers a foreign key cannot be converted: Neo4j constraints
  do not span relationships.

Not converted, and reported: `Bytes`, `Unsupported(…)`, `autoincrement()` and `sequence()` (the id
stays an `Int` without a default: keep the existing ids when you move the data), other
`dbgenerated(…)` defaults, fixed dates as defaults, views, and `@ignore` / `@@ignore` fields and
models. `@map` and `@@map` are reported because Cyphra uses the field and model names as property
names and labels. Composite `type`s (MongoDB) become `Json` fields. `datasource`, `generator` and
native types without an effect (`@db.Uuid`, `@db.Text`) are listed as ignored.

The report has the same three sections as the GraphQL one:

```text
Wrote schema.cyphra (5 node(s), 1 relationship model(s))

Not converted (2):
  Category.id    @default(autoincrement()): Neo4j has no sequences: not converted; keep the existing ids when you migrate the data, and set new ones yourself (or switch to String @id @default(cuid()))
  Product.image  Bytes: Neo4j has no byte arrays in Cyphra: not converted; store the bytes elsewhere (object storage) or as base64 text in a String

Converted with differences (13):
  OrderItem            join model: became relationship OrderItem: (Order)-[:ORDER_ITEM]->(Product) edges with its other fields as properties; Order.items and Product.orderItems now list Product and Order nodes (the properties are on $edge)
  Product.price        Decimal: became Float: a 64-bit float keeps about 15 significant digits, so exact decimals (money) can round; use a String or an Int of cents to keep them exact
  Product.categoryId   foreign key: dropped: the HAS_PRODUCTS edge of category replaces the key (Neo4j links nodes with edges, not key columns)
  …
```

Run `cyphra validate` after the import, then `cyphra migrate dev` for the constraints and indexes.

## Import from neogma

Moving from [neogma](/compare/neogma-neode) to Cyphra? Convert its models to a Cyphra schema:

```bash
cyphra import neogma src/models              # every model file under a folder
cyphra import neogma src/models/user.ts src/models/order.ts --print
```

Pass model files (`.ts`, `.js`, `.mts`, `.cjs`, …) or folders. In a folder, files that do not mention
neogma or TypeBox, tests, `.d.ts` files and `node_modules` are skipped. The options are the ones of
[`cyphra import graphql`](#import-from-neo4jgraphql): `--out <path>`, `--force`, `--merge` and
`--print`.

The importer reads the files with the TypeScript compiler and **never runs them**: no connection to
Neo4j, no import of your app. It follows constants (`const email = Type.String({ … })`, a
`defineRelationshipProperties({ … })` object, a static class field) within the files you pass, so
pass the files that hold the shared schemas too.

What it reads (checked against neogma 2.0.5, November 2026):

- **neogma 2 decorator classes**: `@Node({ label })`, `@PrimaryKey(schema)`, `@Property(schema)` and
  `@Relationship({ name, direction, model, properties })`, from `neogma` (TC39 decorators) or
  `neogma/legacy` (experimental decorators). Without a `label`, the class name is the label, as in
  neogma.
- **`ModelFactory({ label, schema, primaryKeyField, relationships, statics, methods }, neogma)`**,
  the neogma 1 API that neogma 2 still accepts, with revalidator schemas
  (`{ type: 'string', required: true }`) or TypeBox ones, plus `Model.addRelationships({ … })` and hooks or methods assigned to the
  model afterwards.

**Models and properties**

| neogma                                                         | Cyphra                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------ |
| `label: 'User'`                                                | `node User` (a Cyphra model's name is its label)                   |
| `label: ['User', 'Account']`                                   | `node User implements Account`, with an empty `interface Account`  |
| `@PrimaryKey(…)`, `primaryKeyField`                            | `@id`; `format: 'uuid'` also gets `@default(uuid())`, reported     |
| `Type.String()`, `Type.Boolean()`, `Type.BigInt()`             | `String`, `Boolean`, `BigInt`                                      |
| `Type.Number()`                                                | `Float`                                                            |
| `Type.Integer()`, `type: 'integer'`                            | `Int`, reported: the driver stored the JS numbers as `FLOAT`       |
| `Type.String({ format: 'date-time' })`, `format: 'date'`       | `DateTime`, `Date`, reported: stored as strings until you convert  |
| `Type.Array(T)`                                                | `T[]`                                                              |
| `Type.Optional(T)`, `Type.Union([T, Type.Null()])`             | `T?` (an optional list becomes a list, reported)                   |
| revalidator without `required: true`                           | `T?` (revalidator properties are optional by default)              |
| `Type.Union([Type.Literal('a'), …])`, `Type.Enum([…])`, `enum` | an `enum` (values that are not identifiers: a `String` + `@regex`) |
| `Type.Object(…)`, `Type.Record(…)`, `type: 'object'`           | `Json`, reported                                                   |
| no schema (`@Property()`, `Type.Any()`)                        | the type of the field's annotation (`string`, `number[]`, …)       |
| `minLength` / `maxLength`, `allowEmpty: false`                 | `@length(min, max)`                                                |
| `minimum` / `maximum` (`exclusive…` on integers)               | `@min` / `@max`                                                    |
| `format: 'email'`, `'url'` / `'uri'`, `'uuid'`                 | `@email`, `@url`, `@regex` (UUID)                                  |
| `pattern` (a string or a `/…/i` literal)                       | `@regex(pattern, flags)`                                           |
| `minItems` / `maxItems`                                        | `@size(min, max)`                                                  |
| `default`                                                      | `@default(…)`, reported: neogma validates but never fills defaults |

**Relationships**

- Each alias becomes a list field: `Orders: { name: 'PLACED', direction: 'out', model: Orders }`
  gives `Orders Order[] @relationship(type: "PLACED", direction: OUT)`. Field names are the aliases,
  unchanged. `'self'` points to the same node.
- neogma declares each side on its own model. When both sides are declared (`direction: 'out'` on
  one, `'in'` on the other, same `name`), they become two fields over the same edges, which Cyphra
  reads as inverses of each other. A side declared only once stays one field; add the other side to
  the schema if you want it.
- `direction: 'none'` becomes `OUT`, reported: a Cyphra field follows one direction.
- Relationship `properties` (object, array or function form, on either side or both) become one
  [`relationship` model](/schema#relationships) per type and pair of nodes, named after the type
  (`RATED` gives `Rated`). Cyphra uses the stored property name (`rating`), not the neogma alias
  (`Rating`), and the report says so.

Not converted, and reported: hooks (`beforeCreate`, `beforeDelete`; port them to
[query hooks](/client#query-hooks)), statics and instance methods (port them to
[client extensions](/client#extensions)), custom validators (`Type.Refine`, revalidator `conform`),
unions of different types, formats other than the ones above, `multipleOf`, `uniqueItems`, rules on
list elements, and anything the importer cannot read statically (a schema built by a function, a
label from a variable defined elsewhere). Custom error `messages` are listed as ignored.

neogma creates no constraints, while `@id` does: before the first `cyphra migrate dev`, check that the
existing primary keys have no duplicates. The report has the same sections as the other importers:

```text
Wrote schema.cyphra (3 node(s), 1 relationship model(s))

Not converted (6):
  Customer       beforeCreate: hook: not converted; port it to a query hook: db.$extends({ query: { customer: { create, createMany } } })
  Customer       static findByEmail: static method: not converted; add it as a model method: db.$extends({ model: { customer: { findByEmail } } })
  Product.price  Type.Refine: custom validator: not converted; check the value in a query hook (db.$extends({ query }))
  …

Converted with differences (13):
  Customer.id          format: "uuid": neogma does not generate keys: Cyphra now sets a uuid() when create gets no id (you can still pass one)
  Customer.createdAt   format: "date-time": a date-time string became a DateTime (a Neo4j DATETIME): convert the stored strings with datetime() when you move the data
  Contains.quantity    alias: the alias Quantity (on Order.Products) is not kept: Cyphra uses the stored name, $edge: { quantity }
  …
```

Run `cyphra validate` after the import, then `cyphra migrate dev` for the constraints and indexes.
